# Evidence favors a near-vanilla Claude Code

The Claude Code features that hold up best under scrutiny are the plain, built-in ones: give Claude a command it can run to check its own work, keep a short hand-written CLAUDE.md, start a fresh session between tasks, leave the default auto mode on for repositories you trust, and commit to git as your real undo. A second tier is worth adding in your first weeks: reviewing a written plan before multi-file work, two or three hooks, a few manually invoked skills, the local `/code-review` command, a language-server plugin for typed code, a browser check for UI work, and a sandbox as soon as you run unattended or open code you do not trust. Most of the rest (custom subagents, parallel worktrees, headless automation, MCP servers such as Context7, Serena and GitHub MCP, plugins, Superpowers, spec-kit, BMAD and the Ralph loop) pays off only under specific conditions. Agent teams, SuperClaude, claude-mem, host-level `--dangerously-skip-permissions`, unedited `/init` files and large skill or MCP collections are best skipped. Confidence in this ranking is moderate at the top and low further down, because as of 16 November 2026 **no feature or add-on on the list has been tested in a controlled comparison against plain Claude Code** with a short CLAUDE.md, a plan and a test loop. The independent measurements that do exist mostly cut against adding more: instruction files raised cost by about 20% without raising task success, skills failed to trigger about half the time in early-2026 tests, model-written skills made results worse, and the one spec-driven benchmark with a control showed gains inside its own noise band. Vendor numbers are often the only numbers available (auto mode, managed Code Review, tool search, sandboxing), and several headline claims from community tools were unmeasured or later withdrawn. The pattern across the evidence is that features adding a check or a hard rule earn their keep, while features adding more agents or more always-on instructions cost tokens and time for unproven benefit.

## No add-on has been tested against plain Claude Code

Every verdict below carries one of four evidence grades, and the grades matter more than usual here. **Independent** means a measurement or study by someone other than the maker, even when small. **Vendor** means Anthropic or a tool's maintainer describing or measuring its own product. **Practitioner** means a named engineer with a track record reporting hands-on use. **Anecdote** means issue-tracker reports and forum comments. The independent layer is thin: a few academic papers (on instruction files, skills, plans, multi-agent systems and personas), a few one-person benchmarks, and security research that is solid on demonstrated attacks but often published by firms selling a defense. Nothing compares the features against each other on the same tasks.

Three limits apply to the whole report. First, most numbers predate today's defaults. The independent studies ran on 2025 and early-2026 models with 200K-token windows, while current Claude Code starts in auto mode, defers MCP tool definitions by default and runs most models with a 1M-token window, so effects that depend on model capability (skill triggering, the value of explicit planning, context degradation) have probably shifted ([Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)). Second, community sentiment is under-sampled: Reddit was not readable, and Hacker News discussion of several tools was sparse. Third, many short quotations in the underlying research were retrieved through a summarizing fetch tool, so re-check exact wording before quoting it onward.

## Use first: a runnable check, a short CLAUDE.md, fresh sessions, and git

**A command Claude can run to verify its own work is the most consistently recommended practice and has no controlled measurement behind it.** Anthropic's current guidance leads with it and says that if your repository has a check, the single most useful line in CLAUDE.md is the command that runs it ([Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)). Boris Cherny, who created Claude Code, calls verification probably the most important factor and estimates it improves the final result two to three times, a personal estimate rather than a measurement ([Cherny thread, January 2026](https://threadreaderapp.com/thread/2007179832300581177)). The largest documented autonomous build, a $20,000 C compiler written by 16 parallel agents at Anthropic, drew the same lesson: the tests must be nearly perfect or Claude solves the wrong problem ([Anthropic engineering](https://www.anthropic.com/engineering/building-c-compiler)). All of this is vendor and vendor-staff evidence. It ranks first because every source agrees, it costs nothing, and the same idea explains most of what works further down the list.

**A CLAUDE.md is worth having only if it is short and hand-curated.** The best controlled study, from ETH Zurich, found that repository context files do not generally improve task success while raising inference cost by over 20% on average ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). For Claude Code with Sonnet 4.5 on the paper's own benchmark, success was 73.2% with no file, 65.2% with a model-generated file and 70.3% with the developers' own file; the same data show agents do obey these files, using a tool named in the file 1.6 times per task against under 0.01 when it is not named, and that repository overviews do not help the agent navigate ([arXiv 2602.11988, full text](https://arxiv.org/html/2602.11988)). The study measured only whether Python issues got resolved, not whether code followed team conventions or needed fewer corrections, which is what practitioners say the file is for. A Vercel evaluation points to where the value lies: a compressed 8KB documentation index placed in the always-loaded file lifted pass rates on APIs absent from the model's training data from 53% to 100%, though the test was vendor-run and does not name the agent ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). The conclusion is that content selection is everything. Anthropic now says the same: write down only what Claude cannot find by reading the repo, keep the file under 200 lines, stop describing architecture and file layout, and after `/init` "the work is mostly removing lines" ([best practices](https://code.claude.com/docs/en/best-practices); [memory docs](https://code.claude.com/docs/en/memory)). The 200-line figure is a rule of thumb with no adherence measurement behind it; one experienced team keeps its root file under sixty lines ([HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md)).

**`/clear` between unrelated tasks is free and supported from three directions.** Anthropic's guidance says it costs nothing and that after two failed corrections a cleared session with one better prompt works better than a third correction ([best practices](https://code.claude.com/docs/en/best-practices)). Independent research on 18 models found performance degrades as input length grows even on simple tasks, although on retrieval-style tests rather than coding ([Chroma](https://www.trychroma.com/research/context-rot)). The only Claude Code-specific dataset, one developer's telemetry across 2,451 sessions and 873 compaction events, found that **41.9% of user messages in the five steps after an automatic compaction contained a correction, against a 17.7% baseline**; the author sells a tracking product and notes the data are observational ([LangWatch](https://langwatch.ai/blog/context-tax-when-to-compact)). The practical rule is to start fresh rather than lean on compaction, and to write anything worth keeping into a file first. The 2025 advice to micromanage context usage is retired: Anthropic now lists aggressive context management among the things you can stop doing, because 1M-token windows make overflow rare ([best practices](https://code.claude.com/docs/en/best-practices)).

**Keep the default auto mode on for code you trust, and treat git as the only dependable undo.** New terminal sessions now start in auto mode, where a classifier reviews each action in place of a permission prompt ([permission modes docs](https://code.claude.com/docs/en/permission-modes)). The case for it is Anthropic's own study of 1,053 testers, each shown one planted dangerous command: **human reviewers caught 13.6% and auto mode caught 89%**, and separate telemetry shows users approve 93% to 97% of prompts anyway ([Anthropic: auto mode default](https://claude.com/resources/articles/auto-mode-default-in-claude-code)). That is vendor evidence from a company with an interest in the result, but the method is disclosed and independent commentators accept the direction ([Simon Willison](https://simonwillison.net/2026/Aug/8/auto-mode/)). Auto mode is not a security boundary. Anthropic reports a 17% miss rate on a small set of 52 real overeager actions and calls it one layer of defense "not a substitute" for a sandbox ([Anthropic engineering: auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode); [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)), and an independent researcher bypassed it in 3 of 5, 3 of 5 and 4 of 5 attempts using a poisoned local file ([Embrace The Red](https://embracethered.com/blog/posts/2026/breaking-claude-code-opus-5-and-automode/)). Manual approval remains a reasonable choice while you are learning what the agent does or doing sensitive one-off work; it is a weak safety control, not a useless one. Checkpoints do not fill the gap: by Anthropic's documentation they miss files changed only through shell commands, most subagent edits and anything done to remote systems, and open bug reports describe the restore option failing to appear ([checkpointing docs](https://code.claude.com/docs/en/checkpointing); [issue #14002](https://github.com/anthropics/claude-code/issues/14002)). Commit before each task.

## Add next: plan review, two hooks, a few skills, and language tooling

**Reviewing a written plan before large changes is the human checkpoint people actually use.** Anthropic's telemetry shows users reject 39% of proposed plans but only 3% of individual permission requests ([Anthropic: auto mode default](https://claude.com/resources/articles/auto-mode-default-in-claude-code)). Independent research on a different agent found that a good plan improves issue resolution and a poor plan hurts more than no plan at all, which means an unread plan is not a win ([arXiv 2604.12147](https://arxiv.org/abs/2604.12147)). There is no controlled test of Claude Code's plan mode itself, and the feature is thinner than its reputation. Armin Ronacher's reverse-engineering found it to be a short predefined prompt you can replace by asking for a plan file ([Ronacher](https://lucumr.pocoo.org/2025/12/17/what-is-plan-mode/)), the docs say its blocks are not enforced in terminal sessions with bypass permissions available ([permission modes docs](https://code.claude.com/docs/en/permission-modes)), and Anthropic's current best-practices page never mentions it, recommending instead that Claude interview you, write a `SPEC.md`, and build from it in a fresh session ([best practices](https://code.claude.com/docs/en/best-practices)). Cherny said in January 2026 that most of his sessions start in plan mode ([Cherny thread](https://threadreaderapp.com/thread/2007179832300581177)). The sources therefore disagree on emphasis, and the defensible position is narrow: plan first on multi-file or ambiguous work, read the plan, and skip the ritual for small changes. Whether you use plan mode or a markdown file is a matter of taste.

**Hooks are the only way to make a rule deterministic, and two or three are enough.** CLAUDE.md lines are guidance Claude may decide not to apply; a hook always runs, and a hook denial holds even in bypass mode ([hooks guide](https://code.claude.com/docs/en/hooks-guide)). The commonly used ones are a formatter after each edit, a notification when Claude needs input, and optionally a Stop hook that sends Claude back to work until a check passes; Cherny runs the first two himself ([Cherny thread](https://threadreaderapp.com/thread/2007179832300581177)). Anthropic warns against accumulating them, noting that each one occasionally misfires and needs maintenance ([best practices](https://code.claude.com/docs/en/best-practices)). No one has measured whether hooks improve outcomes. The risk is concrete: command hooks execute shell commands with your full user permissions ([hooks reference](https://code.claude.com/docs/en/hooks)), and Check Point Research showed in February 2026 that hook and MCP settings committed to a repository could run commands before the user approved anything, issues since patched ([Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)). Read a repository's `.claude/` directory before trusting it.

**Skills work as manually invoked workflows and fail as passive knowledge.** Custom slash commands have been merged into skills, so a skill you call by name is the current form of a slash command ([skills docs](https://code.claude.com/docs/en/skills)). SkillsBench, the main independent benchmark, found curated skills raised Claude Code's pass rate from 43.0% to 61.2%; software engineering ranked seventh of eight domains for gain (+11.6 points), four or more skills helped less than one to three, and the authors caution that their skills are much higher quality than the ecosystem average ([arXiv 2602.12670](https://arxiv.org/html/2602.12670)). Automatic triggering is the weak point. In one sandboxed test on Sonnet 4.5 the right skill activated only 50% to 55% of the time without a forcing hook ([Scott Spence](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)), and Vercel saw its documentation skill never invoked in 56% of cases, producing no gain over baseline ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). Both tests predate current models, so the rate may have improved. For a newcomer this means writing a skill only when you notice yourself repeating a procedure, and invoking it with `/name`; Cherny's commit-push-PR command, used dozens of times a day, is the model ([Cherny thread](https://threadreaderapp.com/thread/2007179832300581177)).

**Local `/code-review` is a cheap second pass whose accuracy nobody has published.** It reviews your diff in a fresh subagent that never saw the conversation that produced the code, and `/simplify` runs four parallel reviewers for reuse and simplification without looking for bugs ([commands docs](https://code.claude.com/docs/en/commands)). The rationale is sound and the cost is ordinary usage, but there are no precision or recall figures for either. The one academic field study of AI review, on a different tool, found 73.8% of automated comments were resolved while average pull-request closure time rose from under six hours to over eight ([arXiv 2412.18531](https://arxiv.org/abs/2412.18531)). Use it before committing, and read its findings rather than applying them blindly.

**A language-server plugin has the clearest mechanism of any add-on.** The official code-intelligence plugins give Claude go-to-definition, find-references and automatic type errors after each edit; the tool is read-only, the language server binary must be installed separately, and it does not run in cloud sessions ([code intelligence docs](https://code.claude.com/docs/en/plugins/code-intelligence.md)). The only numbers come from one small vendor-run test on a 149K-line TypeScript repository: tool-output tokens fell 31% to 33%, and the language server never missed a reference where Sonnet 4.6 with grep found 249 of 260. Opus 4.8 found everything either way, and the gain required a CLAUDE.md line telling Claude to prefer the language server ([CircleCI](https://circleci.com/blog/claude-code-lsp/)). The benefit is real but modest and shrinks as models improve.

**For web UI work, let Claude see the page, and prefer the CLI form.** Driving a browser closes the loop on whether the interface renders and behaves, the UI equivalent of a test suite. Microsoft's own Playwright MCP README now tells coding-agent users they may be better served by the Playwright CLI plus skills, because the CLI keeps page data out of context unless requested ([microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp); [microsoft/playwright-cli](https://github.com/microsoft/playwright-cli)). No study quantifies how much browser verification improves UI correctness, so this is practitioner and maintainer judgment.

**A sandbox becomes mandatory the moment you run unattended or open untrusted code.** Security practitioners and Anthropic agree that isolation, not model judgment or approval prompts, is the real boundary; Simon Willison's formulation is that running coding agents in a sandbox is the only credible solution ([Willison](https://simonwillison.net/2025/Oct/22/living-dangerously-with-claude/)). The built-in `/sandbox` needs hardening to live up to that. By its documentation it wraps only shell commands, leaves credential files such as `~/.ssh` and `~/.aws/credentials` readable unless you deny them, lets Claude retry a failed command outside the sandbox unless you turn that off, breaks Docker and several macOS tools, and does not run on native Windows ([sandboxing docs](https://code.claude.com/docs/en/sandboxing)). At least three sandbox-escape advisories were published in 2026, all patched through auto-update ([GHSA-ff64-7w26-62rf](https://github.com/anthropics/claude-code/security/advisories/GHSA-ff64-7w26-62rf); [GHSA-7835-87q9-rgvv](https://github.com/anthropics/claude-code/security/advisories/GHSA-7835-87q9-rgvv)). Anthropic's claim that sandboxing cuts permission prompts by 84% is an internal figure with no published method ([Anthropic engineering: sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)). A newcomer working interactively on their own code can defer this; a short deny list for irreversible commands is the lighter first step, understood as a guard rail, since the docs say Bash rules are not a security boundary ([permissions docs](https://code.claude.com/docs/en/permissions)).

## Situational tools pay off only when a specific condition holds

### Delegation and parallelism are capped by your capacity to review

Built-in subagents need no action: Claude already delegates broad searches to its Explore agent. Custom subagents are worth defining only for two or three recurring roles such as a reviewer, a test runner or a verifier. Anthropic's own docs say a subagent buys parallelism or a fresh pair of eyes "but not a smarter answer" and can be slower because it must regather context ([best practices](https://code.claude.com/docs/en/best-practices)), and Willison locates their main value in keeping token-heavy output out of the main conversation ([Willison](https://simonwillison.net/guides/agentic-engineering-patterns/subagents/)). Independent research on multi-agent systems in general found results ranging from +80.8% on decomposable tasks to −70.0% on sequential ones against a single agent ([arXiv 2512.08296](https://arxiv.org/abs/2512.08296)). No benchmark shows subagents improving Claude Code's coding output.

Parallel sessions in worktrees or separate checkouts are a real practice among heavy users. Cherny runs about five local sessions and five to ten in the cloud ([Cherny thread](https://threadreaderapp.com/thread/2007179832300581177)), and independents such as Willison have adopted the pattern while naming the limit: "the natural bottleneck on all of this is how fast I can review the results" ([Willison](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)). All of the evidence is self-report, much of it from the team that builds the tool. Each worktree is a fresh checkout that needs its environment set up, and usage scales with the session count ([worktrees docs](https://code.claude.com/docs/en/worktrees)). A newcomer should wait until reviewing one stream of output feels easy. Third-party orchestrators add little for a Claude-only user now that `claude --worktree` and the research-preview agent view exist ([agent view docs](https://code.claude.com/docs/en/agent-view)). Conductor offers a polished Mac review interface but is closed source, runs agents unsandboxed and is free only for now ([Conductor FAQ](https://www.conductor.build/docs/faq)); its one hands-on review concluded that four agents mean roughly four times the tokens and that the developer is "still the quality gate" ([madewithlove](https://madewithlove.com/blog/conductor-running-multiple-ai-coding-agents-in-parallel.md)). claude-squad covers several vendors' agents from a terminal under an AGPL-3.0 license with a slow release cadence ([claude-squad](https://github.com/smtg-ai/claude-squad)).

Headless `claude -p`, the Agent SDK and GitHub Actions are genuine automation surfaces with thin outcome evidence. The caveats are specific. A headless run skips the workspace-trust dialog and executes a repository's hooks unless you pass `--bare` ([headless docs](https://code.claude.com/docs/en/headless)). Untrusted issue or pull-request text fed into a CI agent's prompt can make it leak secrets when the workflow is opened to users without write access ([Aikido](https://www.aikido.dev/blog/promptpwnd-github-actions-ai-agents)). And billing for programmatic use on subscriptions was announced, paused and amended within 2026 ([Claude support](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-plan)). `/loop` and scheduled tasks are documented conveniences with no practitioner evidence either way; `/loop` needs an open session, expires after seven days and resends full context on each firing ([scheduled tasks docs](https://code.claude.com/docs/en/scheduled-tasks)).

The heavier review and fan-out commands rest entirely on vendor description. Anthropic reports that under 1% of findings from its managed Code Review were marked incorrect by its own engineers, at $15 to $25 and about 20 minutes per review; that figure applies to the managed multi-agent service on Anthropic's code and does not transfer to the local command ([Anthropic: Code Review](https://claude.com/blog/code-review)). `/ultrareview` is a research preview costing typically $5 to $25 per run after three one-time free runs ([ultrareview docs](https://code.claude.com/docs/en/ultrareview)). `/batch`, dynamic workflows and `/deep-research` have no outcome evidence at all; workflows can launch up to 1,000 agents and their large-run warning is advisory only ([workflows docs](https://code.claude.com/docs/en/workflows)). They suit mechanical changes that fan out over many independent items with good tests, which is the task shape the multi-agent research favors.

### MCP servers have lost ground to CLIs and skills

The 2025 complaint that MCP servers consume the context window is partly outdated. Popular servers used to cost 13,000 to 26,000 tokens each in tool definitions ([Anthropic engineering: advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use); [Zechner](https://mariozechner.at/posts/2025-11-02-what-if-you-dont-need-mcp/)), but Claude Code now defers those definitions by default and loads only tool names at startup ([MCP docs](https://code.claude.com/docs/en/mcp)). Anthropic's 85% reduction figure, published for the equivalent API feature, is a vendor number with no independent replication, and deferral does nothing about large tool results such as page snapshots. The more durable finding is practitioner behavior: Armin Ronacher, Simon Willison and Mario Zechner have each moved from MCP servers to command-line tools plus skills for local coding work ([Ronacher](https://lucumr.pocoo.org/2025/12/13/skills-vs-mcp/); [Willison](https://simonwillison.net/2025/Oct/16/claude-skills/)), and the one controlled practitioner benchmark, 120 Claude Code runs of the same tool as MCP server and as CLI, called the comparison "a wash" ([Zechner](https://mariozechner.at/posts/2025-08-15-mcp-vs-cli/)). MCP keeps a defensible niche where no good CLI exists, where there is no shell, or where a team wants centrally managed OAuth access.

Each named server fits that picture. **Context7** has only vendor evidence of benefit: in Upstash's own test, answers using only an outdated API fell from 43 of 94 to 9 of 94, but plain web search did equally well (7 of 94) at roughly ten times the result size, so the gain comes from having a documentation lookup step, with Context7's edge being token efficiency ([Context7](https://context7.com/guides/why-ai-coding-agents-use-outdated-apis)). It also shipped a documented vulnerability, ContextCrush, in which any registered library owner could push instructions to every user who queried that library; it was fixed within days in February 2026 ([Noma Security](https://noma.security/blog/contextcrush-context7-the-mcp-server-vulnerability/)). Add it when you visibly hit outdated-API errors on a fast-moving framework, not by default. **GitHub MCP** adds little over the `gh` CLI in a terminal, and it was the subject of the best-known MCP prompt-injection demonstration, in which a malicious public issue led an agent to leak private repository data ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)); GitHub has since added lockdown mode and content sanitization ([GitHub changelog](https://github.blog/changelog/2025-12-10-the-github-mcp-server-adds-support-for-tool-specific-configuration-and-more)). **Serena** has no independent benchmark, and its own maintainers document that recent Claude Code and Opus versions resist using its tools without extra hooks or a system-prompt override ([Serena docs](https://oraios.github.io/serena/02-usage/030_clients.html)); the official read-only language-server tool now covers most of the navigation case. **Playwright MCP** remains reasonable for long exploratory browser sessions, and Claude in Chrome for pages behind your own login ([Chrome docs](https://code.claude.com/docs/en/chrome)).

Plugins add no capability of their own. They package skills, hooks, subagents and MCP servers for one-command install and team distribution ([plugins docs](https://code.claude.com/docs/en/plugins)). The trust model deserves a newcomer's attention: Anthropic states that an installed plugin can execute arbitrary code with your user privileges and that it does not security-audit MCP servers, and no page defines what the "Anthropic verified" badge requires ([plugin security docs](https://code.claude.com/docs/en/plugins/security.md); [security docs](https://code.claude.com/docs/en/security.md)). Context7 carried official listing status when ContextCrush was found.

### Community frameworks add structure at a measured price

No community framework has shown better outcomes than plain Claude Code with a plan, a short CLAUDE.md and a test loop, and none earns a must-use label. The single benchmark with a no-framework control, run by an engineering-services vendor on 50 Python tickets, found merge rates of 80% to 84% for spec frameworks against 72% for the control, with a stated noise band of ±10 points and a control that did not use plan mode. The control was also fastest (29 minutes median) and close to cheapest ($2.43 per merged ticket, against $3.33 for spec-kit and $4.23 for BMAD) ([Uvik Software](https://uvik.net/blog/spec-driven-development-benchmark/)).

**Superpowers** is the best-supported of the group and still unmeasured. It installs 15 skills that impose brainstorm, written plan, test-driven development in subagents and review, and it is distributed through the official marketplace ([obra/superpowers](https://github.com/obra/superpowers)). Named practitioners praise it ([Evan Schwartz](https://emschwartz.me/a-rave-review-of-superpowers-for-claude-code/); [Willison](https://simonwillison.net/2025/Oct/10/superpowers/)), but neither offers numbers, and the author publishes no benchmark. The complaints are anecdotal yet consistent: slowness, heavy token use in subagent mode, and small changes escalating into a full spec and plan, the subject of one of its most-discussed open issues ([issue #2530](https://github.com/obra/superpowers/issues/2530)). A newcomer who lacks a plan-test-review habit is the user most likely to benefit, at the price of slower sessions.

**The Ralph loop** is a technique, a shell loop that restarts a fresh agent on the same prompt, and it has the most concrete cost data. One team ported six codebases overnight for just under $800, about $10.50 per agent-hour, and got output that was roughly 90% done and needed human finishing ([RepoMirror](https://github.com/repomirrorhq/repomirror/blob/main/repomirror.md)). Its inventor says he would not use it on an existing codebase ([Huntley](https://ghuntley.com/ralph/)), and an experienced user reports that Anthropic's `ralph-loop` plugin, which keeps one session alive with a Stop hook, loses the fresh-context property that makes the technique work ([HumanLayer](https://www.humanlayer.dev/blog/brief-history-of-ralph)). The widely repeated "$50k contract for $297" story rests on a screenshot and is not evidence. Ralph belongs to experienced developers with a clear test oracle and a sandbox.

**spec-kit** and **BMAD-METHOD** draw the most convergent criticism in the whole evidence base. Three independent hands-on reviews found spec-kit produces large volumes of repetitive markdown, is overkill for small and medium work, and does not reliably make the agent follow the spec ([Böckeler, martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); [Marmelab](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html)). The one with timings, run through GitHub Copilot with a Claude model, recorded 33.5 minutes of agent time and about 3.5 hours of review for 689 lines of code, against 8 minutes and a 15-minute review for his usual iterative approach ([Scott Logic](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html)). Thoughtworks later reported value for experienced brownfield teams that customize the templates ([Thoughtworks Radar](https://www.thoughtworks.com/radar/languages-and-frameworks/github-spec-kit)). BMAD was the slowest and most expensive arm in the vendor benchmark for the same merge rate as lighter tools, and one developer reported two days of its workflow on a to-do app producing documents and no code ([Lancrenon](https://guillim.github.io/ai/development/2026/02/08/bmad-method-disappointment.html)). Both suit large features on experienced teams and bury a beginner in documents.

### Built-ins have absorbed most of what the utilities offered

Checkpoints and `/rewind`, `/compact` and auto memory are conveniences to use with their limits in mind. Auto memory is on by default, stores notes on the local machine only, and has no independent quality evaluation ([memory docs](https://code.claude.com/docs/en/memory)); leave it on. Among third-party utilities, **ccusage** still adds something: usage history beyond the seven days `/usage` shows, plus a single view across other vendors' agents. It has zero runtime dependencies, and for subscribers its dollar figures are notional rather than bills ([ccusage](https://github.com/ryoppippi/ccusage); [costs docs](https://code.claude.com/docs/en/costs)). Devcontainers help teams standardize, but even their security-firm maintainers describe a container as "containment, not a strong security boundary" ([Trail of Bits](https://github.com/trailofbits/claude-code-devcontainer)).

## Skip these: agent teams, SuperClaude, claude-mem, and host-level YOLO

**Agent teams** are the weakest-evidenced feature relative to cost. They are experimental and off by default, use about seven times the tokens of a standard session when teammates run in plan mode, and carry documented failures including stuck tasks, overwritten files and teammates lost on resume ([agent teams docs](https://code.claude.com/docs/en/agent-teams); [costs docs](https://code.claude.com/docs/en/costs)). Community reaction was mixed, and no benchmark shows a benefit ([Hacker News](https://news.ycombinator.com/item?id=46902368)). The often-cited compiler built by 16 agents used a custom shell harness, not this feature. Leaving `/effort ultracode` on for routine work belongs in the same category: it plans a multi-agent workflow for every substantive request, for unmeasured gains ([workflows docs](https://code.claude.com/docs/en/workflows)).

**SuperClaude** has no independent hands-on evidence of any kind. Its "30-50% fewer tokens" and "2-3x faster" figures are maintainer claims with no method, its last release appears to date from March 2026, and that release's notes say placeholder code in several advertised components had only then been replaced with working implementations ([SuperClaude repo](https://github.com/SuperClaude-Org/SuperClaude_Framework); [releases](https://github.com/SuperClaude-Org/SuperClaude_Framework/releases)). Its design centers on role personas, and research on persona prompts is mixed to negative: a Wharton study across six models found expert personas gave no consistent accuracy benefit ([arXiv 2512.05858](https://arxiv.org/abs/2512.05858)), while one ACL 2025 paper found task-matched personality prompts improved single-function code generation ([arXiv 2411.00006](https://arxiv.org/abs/2411.00006)). Neither tests persona frameworks on agentic coding, so the honest statement is that SuperClaude's benefit is unproven.

**claude-mem** solves a problem Claude Code now largely handles with built-in auto memory, and its record raises trust questions. The maintainer withdrew its "~10x token savings" claim in November 2026 as not a measured saving ([issue #4138](https://github.com/thedotmack/claude-mem/issues/4138)). A user documented its background observer model draining subscription quota while idle, which led to a lower default ([issue #5023](https://github.com/thedotmack/claude-mem/issues/5023)). And its installer uploaded 30 days of prompts from five coding tools to the cmem.ai cloud service without opt-in until a fix in v15.8.3 ([issue #5176](https://github.com/thedotmack/claude-mem/issues/5176)). These are issue-tracker reports, each confirmed by a maintainer fix. The older concern about its AGPL license is obsolete, since the core is now Apache-2.0 ([claude-mem repo](https://github.com/thedotmack/claude-mem)).

**`--dangerously-skip-permissions` on your own machine** removes every protection against prompt injection, by Anthropic's documentation ([permission modes docs](https://code.claude.com/docs/en/permission-modes)). It has been weaponized: the August 2025 Nx npm malware launched Claude Code with that flag to hunt for wallets and keys ([Snyk](https://snyk.io/blog/weaponizing-ai-coding-agents-for-malware-in-the-nx-malicious-package/)). The popular story that this flag is what deletes home directories is only partly supported. In the two best-documented Claude Code wipes, the reporters say they were not using it, which is further evidence that prompts alone do not protect you ([issue #10077](https://github.com/anthropics/claude-code/issues/10077); [issue #12637](https://github.com/anthropics/claude-code/issues/12637)). The flag is legitimate inside an isolated container or VM and nowhere else.

Several popular habits are also contradicted by the independent evidence. An **unedited `/init` file or a long, architecture-heavy CLAUDE.md** is the configuration the ETH study measured as neutral to negative on success and positive on cost, and a survey of 2,303 real context files found 68.1% contain exactly that architecture content ([arXiv 2511.12884](https://arxiv.org/abs/2511.12884)). **Letting Claude write its own skills** lowered Claude Code's pass rate by 8.1 points in SkillsBench, and large skill libraries defeat themselves because Claude Code drops the descriptions of rarely used skills once the listing exceeds its budget ([arXiv 2602.12670](https://arxiv.org/html/2602.12670); [skills docs](https://code.claude.com/docs/en/skills)). **Installing many MCP servers or browsing third-party marketplaces** multiplies attack surface: a Snyk scan of 3,984 skills in open community registries (not Anthropic's marketplaces) found 36.82% had at least one security flaw and 76 carried confirmed malicious payloads; Snyk sells the scanner it recommends ([Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)). **`/security-review` as a security gate** is unsupported: Anthropic publishes no accuracy data, and the main outside test of Claude Code as a security reviewer, run by a competing vendor with scripted prompts on a 2025 version and model, found a 14% true-positive rate and different findings on identical runs ([Semgrep](https://semgrep.dev/blog/2025/finding-vulnerabilities-in-modern-web-apps-using-claude-code-and-openai-codex)). It is a reasonable extra pass and nothing more. Finally, **ccstatusline** mostly duplicates data the built-in status line already exposes, and its common `npx @latest` setup runs whatever version was published most recently, outside the sandbox, on every repaint ([statusline docs](https://code.claude.com/docs/en/statusline); [sandboxing docs](https://code.claude.com/docs/en/sandboxing); [ccstatusline](https://github.com/sirmalloc/ccstatusline)). No incident involving it was found; pin a version if you want it, or ask `/statusline` to generate a local script.

## A starter setup in order of adoption

On day one, install Claude Code, leave auto mode and auto-update at their defaults, and work inside a git repository, committing before each task. Run `/init`, then cut the result hard: keep the exact test, lint and typecheck commands, any convention Claude could not infer from the code, and nothing that describes architecture or file layout. Aim for well under 200 lines. If the project has no fast automated check, creating one is the most valuable first task you can give Claude. From then on, add a line to CLAUDE.md only when you have corrected the same mistake twice.

Adopt three habits immediately. Run `/clear` between unrelated tasks and after two failed corrections. For anything touching several files or with unclear requirements, ask for a plan through plan mode or a spec file and read it before approving; for small changes, just ask. Run `/code-review` on the diff before you commit.

In the first few weeks, add the pieces that match your work. Set up a formatter hook after edits and a notification hook. Accept the language-server plugin when Claude Code offers it for a typed language, and add one line telling Claude to prefer it. If you build web interfaces, install the Playwright CLI with its skill. Turn any procedure you repeat into a skill you invoke by name, and stop at two or three. Add a short deny list covering force pushes, production deploys and infrastructure teardown. Use `gh` for GitHub, and start with zero MCP servers and zero third-party plugins, adding one only when a specific, recurring need appears and after reading what it installs.

Before your first unattended run or your first session in a repository you do not control, turn on `/sandbox` with credential directories denied for reading, a narrow domain allowlist and unsandboxed retries disabled, or move the work into a container, VM or cloud session. Hold off on parallel sessions until reviewing one agent's output is comfortable, and leave agent teams, workflow frameworks and memory add-ons until a concrete problem makes you go looking for them.

## Conclusion

The useful test for any Claude Code feature is whether it adds a check or adds volume. Tests in the loop, a fresh-context reviewer, a hook that cannot be argued with and a plan a human actually reads all add a check, and they are the items every source converges on. More agents, more always-loaded instructions, more personas and more installed servers add volume, and the evidence for them ranges from task-dependent to absent while their costs are documented. This also explains why the add-on market keeps losing ground: the ideas community tools pioneered (plan before code, skills, loops, memory, worktree orchestration) have been absorbed into the product, so each add-on's margin over the defaults shrinks with every release, and any ranking of them should be re-checked every few months.

Two gaps should temper confidence. Nobody has run the obvious experiment, a framework or add-on against plain Claude Code with a plan, a short CLAUDE.md and a verification loop on current models, so "no evidence of benefit" is the strongest claim available against most of the situational tier, not "evidence of no benefit." And as agents take more actions with fewer prompts, the binding questions shift from capability to trust: provenance badges are not security audits, approval prompts are not boundaries, and the skill that matters most for a newcomer is reading what a tool installs before it runs with their permissions.
