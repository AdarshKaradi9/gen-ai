# Claude Code delegation, automation and parallelism features: how useful are they in practice?

Research date: 16 November 2026. Official docs were fetched on that date and describe Claude Code v2.1.2xx to v2.1.319; the product changes fast, so re-check anything version-specific.

Evidence labels used on every finding:
- **(a)** vendor claim (Anthropic docs, blog, or staff speaking about their own product)
- **(b)** independent measurement or study (flagged where the author is a vendor with a commercial interest)
- **(c)** experienced-practitioner report
- **(d)** anecdote (forum comments, unsourced blog numbers)

"Snippet only" means I saw the claim in a search result but did not fetch the page; treat those as leads, not evidence. Page summaries came through a fetch tool that summarises with a small model, so short quotes are as returned by that tool; long docs pages were read in full.

## Subagents: what is the evidence they improve results versus cost?

### Takeaway
The one well-supported benefit is context isolation (noisy searches, test output and logs stay out of the main conversation), plus parallel read-only exploration; there is no public measurement showing subagents make Claude Code's coding output better. The cost side is better evidenced: Anthropic's own figures put multi-agent systems at about 15x chat token use (versus about 4x for a single agent), Anthropic's docs say a subagent gives "parallelism or a fresh pair of eyes ... but not a smarter answer", and independent research finds multi-agent setups range from large gains on decomposable tasks to large losses on sequential ones.

### Cited Findings

Vendor documentation and vendor measurements
- (a) Stated benefits: "Preserve context", "Enforce constraints" by limiting tools, "Reuse configurations", "Specialize behavior", "Control costs by routing tasks to faster, lower-cost models like Haiku". Built-in subagents are Explore (read-only search), Plan (read-only research in plan mode) and general-purpose. Explore and Plan skip CLAUDE.md and the git status snapshot "to keep research fast and inexpensive". Fetched 16 Nov 2026. — [Claude Code docs: sub-agents](https://code.claude.com/docs/en/sub-agents)
- (a) Stated costs: each subagent "sends its own requests, which count toward the same usage limits as your main conversation"; a non-fork subagent "starts fresh and may need time to gather context" and "doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read". — [Claude Code docs: sub-agents](https://code.claude.com/docs/en/sub-agents)
- (a) Current limits, which contradict older write-ups: subagents can nest "up to three layers below the main conversation", 20 can run concurrently per session, and subagents Claude spawns run in the background by default. Many 2025 articles say subagents cannot spawn subagents or never run in parallel; that is outdated. — [Claude Code docs: sub-agents](https://code.claude.com/docs/en/sub-agents)
- (a) Anthropic's plainest statement of the trade-off: "What they cost you is mostly tokens ... Sometimes it's time as well: a fresh subagent first has to gather context your conversation already had, so it can end up *slower* than doing the task where you are. And by default it's the same model (or a smaller one) on the same task. You get parallelism or a fresh pair of eyes out of it, but not a smarter answer." It lists four cases where they pay off: independent work in parallel, keeping long output out of the main conversation, a reviewer that has not seen how the code was written, and restricting tools. — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- (a) Claude Code now delegates on its own by default ("Claude delegates to subagents and checks in only when it has to"; "Broad codebase searches go to the built-in Explore agent"), so much subagent use needs no user action. — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- (a) Rule of thumb from Anthropic's blog (7 Apr 2026): "When a task requires exploring ten or more files, or involves three or more independent pieces of work, that's a strong signal to direct Claude toward subagents." It warns against delegating dependent steps or small tasks, says "Two subagents editing the same file in parallel is a recipe for conflict", and cautions that defining too many specialist agents makes automatic delegation less reliable. It gives no benchmark data. — [Anthropic blog: subagents in Claude Code](https://claude.com/blog/subagents-in-claude-code)
- (a, with internal measurement) Anthropic's multi-agent research system (13 Jun 2025): "agents typically use about 4× more tokens than chat interactions" and "multi-agent systems use about 15× more tokens than chats". A multi-agent system (Opus 4 lead, Sonnet 4 subagents) beat single-agent Opus 4 by 90.2% on an internal research eval. Token usage alone explained 80% of performance variance on BrowseComp. This is a research (web search) system, not Claude Code, and the eval is internal. — [Anthropic engineering: multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- (a) The same post says where multi-agent is a poor fit: "some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit", and "most coding tasks involve fewer truly parallelizable tasks than research". Reported failure modes include spawning "50 subagents for simple queries", duplicated work, and agents continuing after they had sufficient results. — [Anthropic engineering: multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- (a) Cost-reduction advice: delegate verbose operations (tests, docs fetches, log processing) to subagents so "only a summary returns", and set `model: haiku` for simple subagent tasks. `/usage` shows what share of usage each subagent type takes. — [Claude Code docs: costs](https://code.claude.com/docs/en/costs)

Independent research
- (b) "Towards a Science of Scaling Agent Systems" (Kim et al., arXiv 2512.08296, submitted 9 Dec 2025, v3 8 Apr 2026): 260 configurations across six agentic benchmarks, five architectures and three LLM families. Multi-agent performance relative to a single-agent baseline ranged from +80.8% on decomposable financial reasoning to -70.0% on sequential planning; coordination shows diminishing returns once the single-agent baseline is strong; tool-heavy tasks incur multi-agent overhead; architectures without centralised verification propagate errors more. Conclusion: "architecture-task alignment determines collaborative success". Abstract only was read. — [arXiv 2512.08296](https://arxiv.org/abs/2512.08296)
- (b) "Why Do Multi-Agent LLM Systems Fail?" (Cemri et al., arXiv 2503.13657, 17 Mar 2025, v3 26 Oct 2025): 1,600+ annotated traces from 7 multi-agent frameworks; 14 failure modes in three categories (system design issues, inter-agent misalignment, task verification); notes that gains on popular benchmarks are "often minimal". Uses older models (GPT-4, Claude 3) and does not study Claude Code. Abstract only was read. — [arXiv 2503.13657](https://arxiv.org/abs/2503.13657)

Practitioners and sceptics
- (c, competitor vendor) Cognition's "Don't Build Multi-Agents" (Walden Yan, 12 Jun 2025). Principles: "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results". Its Flappy Bird example has parallel subagents producing mismatched parts. On Claude Code (as of June 2025): the subagent "is usually only tasked with answering a question, not writing any code" and "The benefit of having a subagent in this case is that all the subagent's investigative work does not need to remain in the history of the main agent". The description of Claude Code never running subagents in parallel no longer matches the current docs. Cognition sells a competing agent (Devin). — [Cognition: Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)
- (c) Simon Willison's agentic engineering guide (undated; footer shows 2026): "the main value of subagents is in preserving that valuable root context and managing token-heavy operations". Useful specialist roles he names are code reviewer, test runner and debugger; the test runner's value is that it can "hide the full test output from the main coding agent". He warns "It can be tempting to go overboard breaking up tasks across dozens of different specialist subagents" and that the root agent "is perfectly capable of debugging or reviewing its own output provided it has the tokens to spare". — [Simon Willison: subagents](https://simonwillison.net/guides/agentic-engineering-patterns/subagents/)
- (c, Anthropic staff) Boris Cherny (creator of Claude Code), thread of 2 Jan 2026: he regularly uses two custom subagents, `code-simplifier` (cleans up code after Claude finishes) and `verify-app` (detailed end-to-end testing instructions). — [Thread Reader: Boris Cherny, 2 Jan](https://threadreaderapp.com/thread/2007179832300581177)
- (d) Hacker News thread on agent teams (396 points, 224 comments, about Feb 2026): "Claude Code has already had subagent support" (astrange); "Fancy orchestration is mostly a waste, validation is the bottleneck" (CuriouslyC). — [Hacker News item 46902368](https://news.ycombinator.com/item?id=46902368)
- (d, snippet only) Blog claims of per-subagent overhead conflict (about 5,000 tokens in one post, about 20,000 in another), and one user report describes subagents consuming 160k tokens for work that took 3k in the main context. None were fetched or verified.

### Inferences
- The evidence supports subagents as a context-management tool first and a speed tool second. Nobody, including Anthropic, claims they produce a "smarter answer"; Anthropic's own docs explicitly deny it.
- The 15x figure is often quoted against Claude Code subagents but comes from a different product (a web research system). It is a reasonable upper-bound illustration, not a Claude Code measurement.
- Cognition's critique and Anthropic's guidance converge: delegate read-only, self-contained questions; avoid parallel writers with shared decisions. The independent arXiv result (+80.8% to -70.0% depending on task decomposability) fits the same pattern.
- Because Claude Code now auto-delegates to Explore and forks side tasks by default, the practical question for most users is whether to add custom subagents. The practitioner consensus (Willison, Cherny) is a small number of them: reviewer, test runner or verifier, simplifier.

### Gaps
- No public benchmark compares Claude Code with and without subagents on coding quality, time or total tokens.
- No measured per-subagent token overhead from Anthropic; blog numbers conflict and are unsourced.
- Armin Ronacher's June 2025 "Agentic Coding Recommendations" post does not discuss subagents, so I have no cited view from him on this point.

## Hooks: which are valuable, and what are the failure modes and security concerns?

### Takeaway
Hooks are the only mechanism that makes a rule deterministic rather than a suggestion, and the commonly cited high-value ones are few: format after edits, notify when input is needed, block edits or commands that must never happen, and a Stop hook that forces a check to pass. The main risk is that command hooks run arbitrary shell with the user's full permissions, and repository-committed hooks were a real remote-code-execution vector (Check Point, disclosed Feb 2026, since patched); `claude -p` still runs a repository's hooks without any trust dialog.

### Cited Findings

What hooks are for
- (a) Hooks give "deterministic control: certain actions always happen rather than relying on the LLM to choose to run them". Documented examples: desktop notification when Claude needs input, auto-format after edits, block edits to protected files, re-inject context after compaction, audit configuration changes, reload environment on directory change, auto-approve specific permission prompts. Hook types: command, http, mcp_tool, prompt, agent. — [Claude Code docs: hooks guide](https://code.claude.com/docs/en/hooks-guide)
- (a) Anthropic's guidance on when to use one: "If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook. The reverse holds too: if you have hooks for things that are only preferences, delete them and let Claude decide." And: "a hook is for a rule with *zero* exceptions". — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- (a) A hook `"deny"` holds "even in `bypassPermissions` mode or with `--dangerously-skip-permissions`", so hooks can enforce policy users cannot bypass by changing mode; a hook `"allow"` cannot override deny rules. — [Claude Code docs: hooks guide](https://code.claude.com/docs/en/hooks-guide)
- (a) Stop hook for verification: exit code 2 sends Claude back to work until, for example, the type check passes; if the hook blocks eight stops in a row with no tool call between, Claude Code overrides it and ends the turn. — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- (a) Cost use: a PreToolUse hook can trim test output or grep logs before Claude sees them, "reducing context from tens of thousands of tokens to hundreds" (illustrative, not measured). — [Claude Code docs: costs](https://code.claude.com/docs/en/costs)
- (c, Anthropic staff) Boris Cherny's own setup (2 Jan 2026): a PostToolUse hook formats Claude's code, handling "the final 10%" so CI does not fail on formatting; system notifications tell him when a session needs input; an agent Stop hook is one of three ways he keeps long-running tasks going. — [Thread Reader: Boris Cherny, 2 Jan](https://threadreaderapp.com/thread/2007179832300581177); corroborated by [InfoQ, 10 Jan 2026](https://www.infoq.com/news/2026/01/claude-code-creator-workflow)

Failure modes and maintenance cost
- (a) Documented limitations: `PostToolUse` hooks "can't undo actions since the tool has already executed"; `Stop` hooks fire "whenever Claude finishes responding, not only at task completion"; when several PreToolUse hooks rewrite the same input, Claude Code does not merge them or guarantee which wins; default command-hook timeout is 10 minutes. — [Claude Code docs: hooks guide](https://code.claude.com/docs/en/hooks-guide)
- (a) Prompt and agent hooks are not deterministic ("asks *another model* to decide"), and agent hooks are marked experimental: "For production workflows, prefer command hooks". — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices); [Claude Code docs: hooks reference](https://code.claude.com/docs/en/hooks)
- (a) Anthropic warns against overuse: "Every hook and deny rule will occasionally fire when it shouldn't, and someone has to maintain each one. If you ever find yourself at forty of them, most are probably preferences that Claude could have weighed on its own." — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)

Security
- (a) "Command hooks execute shell commands with your full user permissions. They can modify, delete, or access any files your user account can access. Review and test all hook commands before adding them to your configuration." — [Claude Code docs: hooks reference](https://code.claude.com/docs/en/hooks)
- (a) Workspace trust: in interactive sessions hooks are held back until the trust dialog is accepted. In "`-p` or SDK session: Claude Code never shows the dialog and treats the folder as trusted, so hooks committed in a repository's `.claude/settings.json` run in a folder you've never trusted". Mitigations named: review `.claude/` first, use `--bare`, or pass `--settings '{"disableAllHooks": true}'`. — [Claude Code docs: hooks reference](https://code.claude.com/docs/en/hooks); same warning in [Claude Code docs: headless](https://code.claude.com/docs/en/headless)
- (a) Committed `.claude/settings.json` hooks "apply to everyone who works in the repo" once committed. — [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- (b, security vendor research) Check Point Research, "Caught in the Hook" (25 Feb 2026, Aviv Donenfeld and Oded Vanunu), three issues, all patched: (1) a `SessionStart` hook in a repository's `.claude/settings.json` ran commands before the user approved anything, giving remote code execution (advisory GHSA-ph6w-f82w-28w6, published 29 Aug 2025); (2) MCP consent bypass via `enableAllProjectMcpServers` / `enabledMcpjsonServers` in repo settings (CVE-2025-59536; reported 3 Sep 2025, fixed 22 Sep 2025); (3) API key exfiltration via `ANTHROPIC_BASE_URL` in project config, sent before the trust decision (CVE-2026-21852; reported 28 Oct 2025, fixed 28 Dec 2025). Anthropic's fixes: a more explicit trust dialog, MCP servers cannot start before approval, and no network requests before trust is accepted. Conclusion: configuration files "are no longer passive metadata" and should be reviewed like source code. — [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)
- Conflict to note: secondary coverage (seen in search snippets only, for example The Hacker News) attributes CVE-2025-59536 with CVSS 8.7 to the hooks issue and gives fixed versions 1.0.87 and 2.0.65. The primary Check Point article, as fetched, ties CVE-2025-59536 to the MCP consent bypass and gives no CVSS scores or version numbers. Verify against the GitHub advisories before quoting CVE-to-issue mappings.

### Inferences
- Hooks are probably the highest value-per-effort feature in this set for anyone past the beginner stage: one formatter hook and one notification hook cost minutes, use no model tokens, and are endorsed by both the docs and the tool's creator.
- The interactive-session attack surface was closed by the trust dialog fixes, but the residual risk is real and documented: scripted `claude -p` over an untrusted repository executes that repository's hooks. Anyone running headless Claude Code over third-party code should use `--bare` or disable hooks.
- Value falls off quickly with volume. Anthropic's own "forty hooks" warning suggests a handful of zero-exception rules is the sensible ceiling.

### Gaps
- No independent measurement of whether hooks improve outcomes (for example fewer CI failures); evidence is vendor guidance plus practitioner habit.
- I did not find practitioner reports from Armin Ronacher or Simon Willison specifically on hooks in pages I fetched.
- I did not fetch the GitHub advisories themselves, so exact affected and fixed version numbers are unverified.

## Worktrees and parallel sessions: what do the Claude Code team and practitioners report, and what are the limits?

### Takeaway
The Claude Code team presents parallel sessions as their top productivity practice (Boris Cherny runs about 5 local and 5 to 10 web sessions), and experienced independents such as Simon Willison and Armin Ronacher have adopted parallel agents too, but all of the evidence is self-report. The consistent limit across sources is human review capacity, followed by environment setup per worktree and usage cost; no source offers a controlled measurement of the gain.

### Cited Findings

Claude Code team (vendor-affiliated practitioners)
- (c, Anthropic staff) Boris Cherny, 2 Jan 2026: runs 5 local Claudes in numbered terminal tabs plus 5 to 10 on claude.ai/code, uses system notifications to know when one needs input, starts most sessions in plan mode, and says giving Claude a way to verify its work "will 2-3x the quality of the final result" (his estimate, not a measurement). — [Thread Reader: Boris Cherny, 2 Jan](https://threadreaderapp.com/thread/2007179832300581177)
- (c, reporting vendor practice) InfoQ (10 Jan 2026): each of his local sessions uses its own git checkout rather than worktrees, and around 10 to 20% of his remote sessions are abandoned. — [InfoQ](https://www.infoq.com/news/2026/01/claude-code-creator-workflow)
- (a/c) Boris Cherny, 21 Feb (2026) thread announcing built-in worktree support (`claude --worktree`, `--tmux`, `isolation: worktree` for subagents, hooks for non-git VCS; version 2.1.50): "agents can run in parallel without interfering with one other". The Thread Reader page also shows an excerpt of a separate 31 Jan thread calling 3 to 5 parallel worktrees the team's top tip and "the single biggest productivity unlock"; I saw only that excerpt, not the full 31 Jan thread. — [Thread Reader: Boris Cherny, 21 Feb](https://threadreaderapp.com/thread/2025007393290272904.html)
- (c, reporting vendor claims) Pragmatic Engineer (23 Sep 2025, partly paywalled): Cherny says "around 90% of Claude Code is written with Claude Code"; engineers pushed about 5 PRs per day; PR throughput rose 67% while the engineering team doubled. The article itself cautions the 67% may partly reflect a "lucky constellation of events". — [Pragmatic Engineer: How Claude Code is built](https://newsletter.pragmaticengineer.com/p/how-claude-code-is-built)

Independent practitioners
- (c) Simon Willison, "Embracing the parallel coding agent lifestyle" (5 Oct 2025): initially sceptical because review is the limit, now works this way. Tasks that parallelise well: research and proofs of concept, explanations of how existing code works, low-stakes maintenance (for example fixing deprecation warnings), and carefully specified work. "the natural bottleneck on all of this is how fast I can review the results." He can only land one significant change at a time. He had not adopted worktrees and uses a fresh checkout, often in `/tmp`. — [Simon Willison, 5 Oct 2025](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)
- (c) Armin Ronacher (12 Jun 2025): "Agents aren't exceptionally fast individually, but parallelization boosts overall efficiency." He starts from a second checkout, says shared state (file system, databases, Redis) must be managed for several agents to run, and that pushing work into CI-style background agents "isn't working" for him yet. He expected the post to "age very poorly". — [Armin Ronacher: Agentic Coding Recommendations](https://lucumr.pocoo.org/2025/6/12/agentic-coding/)
- (d) Hacker News (about Feb 2026, 224 comments): one commenter reports the bottleneck shifting to their own review capacity; "It does use up tokens incredibly fast" (doctoboggan); "I absolutely cannot trust Claude code to independently work on large tasks" (ottah). — [Hacker News item 46902368](https://news.ycombinator.com/item?id=46902368)

Mechanics and documented limits
- (a) `claude --worktree <name>` creates `.claude/worktrees/<name>/` on branch `worktree-<name>`. "A worktree is a fresh checkout, so initialize your development environment there"; gitignored files such as `.env` are absent unless listed in `.worktreeinclude`. — [Claude Code docs: worktrees](https://code.claude.com/docs/en/worktrees)
- (a) Gotchas: new worktrees branch from the repository's default branch on the remote, not from your current work, unless `worktree.baseRef` is `"head"`; worktrees share the main `.git` directory and saved permission approvals; Git LFS files set up with `--local` arrive as pointer files; `-p` runs do not clean up their worktrees; hook paths (`${CLAUDE_PROJECT_DIR}`) keep pointing at the main checkout. — [Claude Code docs: worktrees](https://code.claude.com/docs/en/worktrees)
- (a) Isolation checks block edits and git redirection into the main checkout but do not track what a shell command writes, so `cp` or a redirect into the main checkout is not refused by them. — [Claude Code docs: worktrees](https://code.claude.com/docs/en/worktrees)
- (a) Cost context: enterprise average is "around $13 per developer per active day and $150-250 per developer per month, with costs remaining below $30 per active day for 90% of users"; costs vary with "running multiple instances or automation". Subscription usage is shared across sessions. — [Claude Code docs: costs](https://code.claude.com/docs/en/costs)

### Inferences
- Parallel sessions are a real practice among heavy users, not marketing only, but the headline numbers (5 PRs a day, 5 to 15 sessions) come from the team that builds the tool, with unusually good tests, tooling and unlimited usage. They should not be read as typical.
- The limit is the reviewer, not the agent. Willison, HN commenters and Anthropic's own Code Review launch (which cites review becoming a bottleneck as output rose) all point the same way. Parallelism pays when tasks are independent, well specified and cheap to verify.
- Whether to use git worktrees specifically is a convenience choice: Cherny and Willison both use plain separate checkouts. The built-in `--worktree` flag lowers setup friction but adds its own surprises (base branch, missing `.env`, per-worktree dependency installs).
- Merge conflicts are an obvious risk when parallel sessions touch overlapping files; sources mention conflict avoidance by task selection rather than reporting conflict rates.

### Gaps
- No controlled or independent measurement of throughput or defect rates from running parallel sessions.
- No data on merge-conflict frequency or on the cost multiple of running N sessions (it should scale roughly linearly, but nobody publishes figures).
- The full 31 Jan 2026 Cherny thread was not fetched.

## Headless mode, Agent SDK, GitHub Actions and scheduled tasks: documented uses, cost and safety caveats

### Takeaway
These are well-documented, real automation surfaces (CI review, `@claude` on issues and PRs, piping logs and diffs through `claude -p`, scheduled reports, large scripted migrations), and the Claude Code team uses them, but public outcome evidence is thin beyond Anthropic's own examples. The caveats are concrete: every run consumes tokens (and Actions minutes), headless runs skip the workspace-trust dialog, and AI agents in CI are a demonstrated prompt-injection target.

### Cited Findings

Headless mode and Agent SDK
- (a) `claude -p` is the CLI face of the Agent SDK ("the same tools, agent loop, and context management that power Claude Code"), for scripts and CI/CD. Documented patterns: pipe a build log in for a root-cause explanation, use as a project-specific linter in a `package.json` script, create a commit from staged changes, review a PR diff for security issues, structured JSON output with `--json-schema`. — [Claude Code docs: headless](https://code.claude.com/docs/en/headless)
- (a) Safety: without `--bare`, a `-p` session "runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted". `--bare` "is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release". Since v2.1.302, `-p` runs start in Manual mode, where calls needing approval are denied unless something approves them. — [Claude Code docs: headless](https://code.claude.com/docs/en/headless)
- (a) Cost controls: `--output-format json` returns `total_cost_usd` (a client-side estimate); `--max-budget-usd` caps a run; `--max-turns` limits iterations. — [Claude Code docs: headless](https://code.claude.com/docs/en/headless)
- (a) Billing status: Anthropic's support page says (15 Jun 2026) "We've paused the previously-announced changes to Claude Agent SDK usage" and "nothing has changed: Claude Agent SDK, `claude -p`, and third-party app usage still draw from your subscription limits". A 7 Oct 2026 update says Max, Ultra and Team plans now include monthly API credits usable with an API key. The originally announced separate credit amounts ($20 Pro, $100 Max 5x, $200 Max 20x from 15 Jun 2026) appeared only in search snippets of third-party blogs. This area has changed twice in 2026; re-check before relying on it. — [Claude support: Agent SDK with your plan](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-plan)
- (a, with measured figures) Largest documented headless use: Nicholas Carlini (Anthropic, 5 Feb 2026) ran 16 parallel Claude agents in a bash loop inside Docker containers, nearly 2,000 Claude Code sessions, about 2 billion input and 140 million output tokens, about $20,000, producing a roughly 100,000-line Rust C compiler that builds Linux 6.9. This was a custom harness with lock files in a shared git repo and no orchestrator, not the agent teams feature. Lessons: "Test verifiers must be nearly perfect, or Claude will solve the wrong problem". Admitted limits: no finished assembler or linker, inefficient generated code, not a drop-in GCC replacement. — [Anthropic engineering: building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)

GitHub Actions
- (a) `claude-code-action` responds to `@claude` in issues and PRs, turns issues into PRs, runs skills such as code review on PR events, and runs prompts on a cron schedule (example: a daily summary of commits and open issues). — [Claude Code docs: GitHub Actions](https://code.claude.com/docs/en/github-actions)
- (a) Cost: each run consumes GitHub Actions minutes and API tokens (or subscription usage with an OAuth token). Recommended controls: `--max-turns`, workflow-level timeouts, concurrency limits, concise CLAUDE.md. No typical per-run cost is published. — [Claude Code docs: GitHub Actions](https://code.claude.com/docs/en/github-actions)
- (a) Built-in safeguards: the triggering user must have write access; bot actors are rejected unless listed in `allowed_bots`; on public repos GitHub withholds secrets from fork PRs, so the review workflow runs only on same-repo branches. The official Claude GitHub App requests a broad permission set (including Contents, Actions and Workflows read/write) that cannot be partially accepted; a custom app with fewer permissions is the alternative. — [Claude Code docs: GitHub Actions](https://code.claude.com/docs/en/github-actions)
- (b, security vendor research) Aikido Security, "PromptPwnd" (4 Dec 2025, updated 17 Mar 2026): untrusted issue titles, PR descriptions or commit messages inserted into AI prompts in GitHub Actions or GitLab CI can make the agent leak secrets or alter repositories. For Claude Code Action the default (write-permission users only) is the boundary; setting `allowed_non_write_users: "*"` removes it, which Aikido calls "extremely dangerous" because a privileged `$GITHUB_TOKEN` is then almost always leakable. At least five Fortune 500 companies were affected across the tools studied (Gemini CLI, Claude Code Actions, OpenAI Codex Actions, GitHub AI Inference). Mitigations: restrict agent tools, do not inject untrusted input into prompts, treat AI output as untrusted, limit token blast radius. — [Aikido: PromptPwnd](https://www.aikido.dev/blog/promptpwnd-github-actions-ai-agents)
- (c, Anthropic staff) Real use by the Claude Code team: Cherny tags `@.claude` on coworkers' PRs via the GitHub action to add learnings to the shared CLAUDE.md. — [Thread Reader: Boris Cherny, 2 Jan](https://threadreaderapp.com/thread/2007179832300581177)

Scheduled tasks and /loop
- (a) Three options: cloud scheduled tasks (run without your machine, fresh clone, minimum interval 1 hour), Desktop scheduled tasks (local, machine must be on), and `/loop` (session-scoped, minimum 1 minute, needs an open session). Named uses: poll a deployment, babysit a PR, check a long build, reminders. — [Claude Code docs: scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)
- (a) `/loop` limits: recurring tasks expire after 7 days; up to 50 tasks per session; no catch-up for missed fires; fires only while Claude Code is running and idle; a self-paced loop is not restored on `--resume`; run times are jittered (hourly tasks can start up to 30 minutes late). — [Claude Code docs: scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)
- (a) Cost caveat: a session-scoped scheduled task "fires on its interval even while the session is idle, sending your full context each time"; `/usage` lists the heaviest loops. The docs also note the Monitor tool "avoids polling altogether and is often more token-efficient". — [Claude Code docs: costs](https://code.claude.com/docs/en/costs); [Claude Code docs: scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)

### Inferences
- Headless mode is the building block the other automation features sit on (GitHub Actions is built on the SDK; Carlini's compiler was a bash loop over it). Its value depends entirely on the quality of the verification around it, which is Carlini's main lesson.
- For CI use, the safe default is narrow: read-only review jobs, trusted triggering users, `--bare` or hooks disabled for third-party code, explicit turn and budget caps. The Aikido research shows the dangerous configurations are opt-in, but they are one setting away.
- `/loop` is a convenience for short-lived polling inside a session. Its 7-day expiry, need for an open session and full-context cost per firing make it a poor fit for durable automation; the docs themselves redirect to cloud tasks or GitHub Actions for that.
- Subscription billing for programmatic use is unstable policy (announced, paused, then supplemented with API credits within five months). Teams building on `claude -p` with a subscription should plan for change.

### Gaps
- No independent data on issue-triage or CI-review outcomes with claude-code-action (acceptance rates, cost per run).
- No practitioner evidence found on scheduled tasks or `/loop` usefulness; everything is from the docs.
- The claude-code-action security documentation on GitHub was not fetched.
- Agent SDK (Python and TypeScript packages) adoption and outcomes outside Anthropic were not researched in depth.

## Bundled review commands: is there evidence on accuracy and false positives, and what does ultrareview cost?

### Takeaway
Anthropic has published headline numbers only for its managed, multi-agent Code Review service (under 1% of findings marked incorrect internally, 16% to 54% of PRs getting substantive comments, $15 to $25 per review); there are no published accuracy figures for the local `/code-review`, `/security-review`, `/simplify` or ultrareview. The few outside evaluations of Claude Code as a security reviewer come from security vendors, use old models, and found it noisy (14% true-positive rate in Semgrep's test) and non-deterministic.

### Cited Findings

What the commands are
- (a) `/code-review` (alias `/review`): reviews the current diff, a PR, branch or path for correctness bugs at an effort level (low to max, or `ultra` for the cloud review); `--fix` applies findings, `--comment` posts them. It runs "in a fresh subagent that never saw your conversation", so "It isn't swayed by the reasoning that produced the code". Counts toward normal usage. — [Claude Code docs: commands](https://code.claude.com/docs/en/commands); [Claude Code docs: best practices](https://code.claude.com/docs/en/best-practices)
- (a) `/simplify`: "Four review agents run in parallel, covering reuse of existing helpers, simplification, efficiency, and whether the change is at the right level of abstraction. The review doesn't look for correctness bugs." — [Claude Code docs: commands](https://code.claude.com/docs/en/commands)
- (a) `/security-review`: analyses the diff between your branch and origin's default branch for "risks like injection, auth issues, and data exposure". — [Claude Code docs: commands](https://code.claude.com/docs/en/commands)
- (a) `/batch`: decomposes a large change into 5 to 30 independent units, then spawns one background subagent per unit in its own worktree; each implements, runs tests and opens a PR. — [Claude Code docs: commands](https://code.claude.com/docs/en/commands)
- (a) `/deep-research`: a bundled dynamic workflow that fans out web searches, cross-checks sources, votes on each claim and returns a cited report with unverified claims marked. — [Claude Code docs: workflows](https://code.claude.com/docs/en/workflows)

Anthropic's published figures (managed Code Review, Team and Enterprise)
- (a, internal measurement) Launch post, 9 Mar 2026: at Anthropic, PRs receiving substantive review comments rose from 16% to 54%; on PRs over 1,000 lines, 84% get findings averaging 7.5 issues; on PRs under 50 lines, 31% get findings averaging 0.5; "less than 1%" of findings were marked incorrect by engineers; average review takes about 20 minutes and costs $15 to $25, scaling with size. Context given: code output per Anthropic engineer grew 200% in a year, making review a bottleneck. Examples: a one-line change flagged as breaking authentication; a pre-existing type mismatch found in TrueNAS middleware. — [Anthropic blog: Code Review](https://claude.com/blog/code-review)
- (a) How it works: several agents examine the diff in parallel, a verification step "filters out false positives", findings are deduplicated and ranked by severity; it never approves or blocks a PR and reads code without building or running it. Disclaimer: "A review with no findings doesn't mean your code is error-free or secure." Not available with Zero Data Retention, HIPAA configuration or CMEK. — [Claude Code docs: Code Review](https://code.claude.com/docs/en/code-review)
- (a) Billing: no flat price; billed on tokens through usage credits, separately from plan usage, to the organisation. The default trigger for a newly added repo is "After every push", "multiplying cost by the number of pushes". An organisation-wide monthly spend limit is available. — [Claude Code docs: Code Review costs](https://code.claude.com/docs/en/code-review-costs)

Ultrareview
- (a) Research preview ("pricing, and availability may change"). `/code-review ultra` (alias `/ultrareview`) launches "a fleet of reviewer agents in a cloud sandbox"; "every reported finding is independently reproduced and verified". Three free runs per account on Pro, Max and Ultra (one-time, do not refresh), then "typically $5 to $25 in usage credits depending on the size of the change"; a run counts once the cloud session starts, even if stopped. Takes about 5 to 15 minutes. Limits: 500 changed files and 8,000 changed lines by default. Requires a claude.ai login; unavailable on Bedrock, Google Cloud or Foundry, or with ZDR, HIPAA or CMEK. Claude never starts one on its own. — [Claude Code docs: ultrareview](https://code.claude.com/docs/en/ultrareview)
- (a) Positioning against local review: local `/code-review` is "seconds to a few minutes", best "for quick feedback while iterating"; ultrareview is for "pre-merge confidence on substantial changes". No accuracy or recall figures are given for either. — [Claude Code docs: ultrareview](https://code.claude.com/docs/en/ultrareview)

Security review evidence
- (a) Launch post, 6 Aug 2025: `/security-review` and a GitHub Action check SQL injection, XSS, auth flaws, insecure data handling and dependency vulnerabilities; the Action "Applies customizable rules to filter out false-positives". Internal examples: a DNS-rebinding remote code execution bug and an SSRF caught before merge. No accuracy metrics are given. — [Anthropic blog: automate security reviews](https://claude.com/blog/automate-security-reviews-with-claude-code)
- (b, security vendor with a competing product; old versions) Semgrep (2 Sep 2025): Claude Code v1.0.32 with Sonnet 4, 11 large open-source Python web apps, one scripted prompt per vulnerability class, findings manually triaged. Claude Code reported 46 real vulnerabilities at a 14% true-positive rate (86% false positives) overall; by class: IDOR 22%, XSS 16%, SQL injection 5%. Identical prompts on one app produced 3, 6 and 11 findings across three runs. On `/security-review` itself, run over whole codebases on three apps, it "found only one XSS in total". Conclusion: results "may be quite noisy", models struggle with inter-procedural taint flow. Note that `/security-review` is designed for branch diffs, not whole-repository audits, so that part of the test is somewhat off-label. — [Semgrep](https://semgrep.dev/blog/2025/finding-vulnerabilities-in-modern-web-apps-using-claude-code-and-openai-codex)
- (b, weak; security vendor promoting its own product) Bright Security (28 May 2026): five AI security reviews of one roughly 300-line app generated with Claude Code (Opus 4.6) with planted flaws; 60% of findings classed as false positives, 60% of scans missed the planted criticals, about 30% of findings consistent across runs. The article does not say whether `/security-review` or a general prompt was used. A single tiny app; treat as an anecdote with numbers. — [Bright Security](https://brightsec.com/blog/ai-security-review-fails-in-practice-claude-opus-4-6-missed-critical-vulnerabilities-generated-dangerous-false-positives/)
- (b, snippet only) DeepSource, a competitor, reports Claude Code (Opus 4.5) at F1 62.40% on the OpenSSF CVE benchmark versus its own 84.51%. Not fetched.

AI code review generally (not Claude-specific)
- (b) "Automated Code Review In Practice" (Cihan et al., ICSE 2025 SEIP track, arXiv 2412.18531, Dec 2024): industrial deployment of an LLM reviewer based on Qodo PR-Agent; about 238 practitioners had access, 4,335 PRs studied of which 1,568 got automated reviews. 73.8% of automated comments were resolved, and most practitioners reported a minor code-quality improvement, but average PR closure time rose from 5 h 52 min to 8 h 20 min, with faulty reviews, unnecessary corrections and irrelevant comments reported. Abstract only was read. — [arXiv 2412.18531](https://arxiv.org/abs/2412.18531)
- (b, snippet only) Reported Atlassian studies (18.2% of LLM reviewer comments bug-related versus 6.5% for humans; 38.7% of generated comments triggered code changes) and a 239-repository study (36.4% of agent comments accepted, 56.3% rejected) were seen only in secondary write-ups; originals not verified.

Practitioner signal
- (c, Anthropic staff) Cherny uses a `code-simplifier` subagent after Claude finishes, the same idea as `/simplify`. — [Thread Reader: Boris Cherny, 2 Jan](https://threadreaderapp.com/thread/2007179832300581177)

### Inferences
- The "under 1% marked incorrect" figure applies to the managed, verified, multi-agent service on Anthropic's own code, where "marked incorrect" depends on engineers bothering to mark things. It should not be transferred to local `/code-review` or `/security-review`, which have no published accuracy data.
- Independent academic evidence on AI code review is mixed rather than negative: most comments get acted on, but review can lengthen PR cycle time. That is consistent with Anthropic choosing a slow (about 20 minutes), expensive, verified design to keep noise down.
- For security, the available outside evidence says "useful second pass, not a scanner": real bugs are found, but with high noise and run-to-run variance in the tested versions. Those tests predate current models by a year or more, so the numbers are likely pessimistic for today's product, but no newer independent evaluation was found.
- Local `/code-review` is the cheap, defensible default (fresh-context reviewer, normal usage). Ultrareview at $5 to $25 a run after three one-time free runs is plausibly worth it for large or risky merges but rests entirely on vendor description.
- `/simplify`, `/batch` and `/deep-research` have no outcome evidence at all; they are packaged versions of patterns (parallel reviewers, worktree fan-out, cross-checked research) whose value depends on the task.

### Gaps
- No independent evaluation of `/code-review`, managed Code Review, or ultrareview accuracy (precision or recall) was found.
- No evaluation of `/security-review` on its intended use (branch diffs) with current models. One commentator, seen in a snippet only, said Anthropic declined to share false-positive figures.
- No evidence on `/simplify` or `/batch` outcomes; no cost figures for `/batch` (it should scale with 5 to 30 subagents plus one PR each).
- The docs page for local `/code-review` (`code-review-local`) was not fetched, so effort-level details are from the commands table only.

## Agent teams and dynamic workflows: experimental status, cost, and evidence of worth

### Takeaway
Agent teams are explicitly experimental and off by default, cost roughly a multiple of a single session per teammate (Anthropic cites about 7x when teammates run in plan mode), and have documented reliability gaps; the evidence they are worth it is limited to vendor examples and mixed anecdotes. Dynamic workflows are generally available on paid plans and are the more controllable way to run many agents (scripted, resumable, capped), but they have no outcome evidence beyond Anthropic's description and can consume tokens very quickly.

### Cited Findings

Agent teams
- (a) Status: "Agent teams are experimental and disabled by default. Enable them by setting `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`". They "have known limitations around session resumption, task coordination, and shutdown behavior". — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)
- (a) Where they fit: research and review, new modules with separate owners, debugging with competing hypotheses, cross-layer changes. "Agent teams add coordination overhead and use significantly more tokens than a single session ... For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective." — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)
- (a) Cost: "Agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode"; "Token costs scale linearly" with teammates; each active teammate keeps consuming tokens until it exits. Advice: use Sonnet for teammates, start with 3 to 5, "Three focused teammates often outperform five scattered ones". — [Claude Code docs: costs](https://code.claude.com/docs/en/costs); [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)
- (a) Documented limitations: in-process teammates are not restored by `/resume` or `/rewind`; "teammates sometimes fail to mark tasks as completed, which blocks dependent tasks"; slow shutdown; one team per session; no nested teams; no per-teammate permission modes at spawn; "Two teammates editing the same file leads to overwrites"; the lead may start implementing instead of waiting, or declare the team finished early; teammates "may stop after encountering errors instead of recovering". — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)
- (a) Side effect of enabling: "teams can form even when you didn't ask for one", because any subagent Claude names launches as a teammate; and a teammate's plan is auto-approved without the lead reviewing it unless you changed its permission mode. Teams do not spawn in `-p` or Agent SDK sessions. — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)
- (a) Anthropic's own advice for newcomers is to start with tasks that "don't require writing code: reviewing a PR, researching a library, or investigating a bug". — [Claude Code docs: agent teams](https://code.claude.com/docs/en/agent-teams)
- (a, measured but not this feature) The often-cited "agent team" compiler project (16 agents, about $20,000, about 2,000 sessions) used a custom bash-loop harness with no orchestrator, not the agent teams feature. — [Anthropic engineering: building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- (d) Hacker News launch thread (396 points, 224 comments): mixed. Positive ("this blows it out of the water", MarkMarine); cost complaints ("It does use up tokens incredibly fast", doctoboggan); scepticism ("Fancy orchestration is mostly a waste, validation is the bottleneck", CuriouslyC; "I absolutely cannot trust Claude code to independently work on large tasks", ottah). Several said they had built similar tmux or script setups already. Only the first 100,000 characters of the thread were read. — [Hacker News item 46902368](https://news.ycombinator.com/item?id=46902368)
- (c, weak; opinion essay without own measurements) Nick Sawinyh (9 Sep 2026) argues teams justify their cost through structured disagreement (competing-hypothesis debugging, multi-lens review), and that parallel implementation is "the weak case"; cites a practitioner estimate of three to four times a single session's cost, "not a documented figure". — [sawinyh.com](https://sawinyh.com/blog/claude-code-agent-teams-buy-disagreement)
- (d, snippet only) Secondary reports: 4 agents on 6 tasks in a roughly 50K-line FastAPI codebase took about 6 minutes versus 18 to 20 sequentially at roughly 4x tokens; one incident triage took about 10 minutes versus 30 to 45 at $8 to $10 versus $2 to $3; one post describes spending $150 in three hours. Originals not fetched.
- (b) Independent research relevant to coordination: multi-agent results range from +80.8% (decomposable tasks) to -70.0% (sequential planning) against a single agent, and architectures without centralised verification propagate errors more. — [arXiv 2512.08296](https://arxiv.org/abs/2512.08296). The MAST taxonomy lists inter-agent misalignment and task verification among its three failure categories. — [arXiv 2503.13657](https://arxiv.org/abs/2503.13657)

Dynamic workflows
- (a) Status: not labelled experimental; "available on all paid plans, with Anthropic API access, and on Amazon Bedrock, Google Cloud's Agent Platform, and Microsoft Foundry. On Pro, turn them on from the Dynamic workflows row in `/config`." A workflow is a JavaScript script Claude writes that orchestrates subagents; "Claude's context holds only the final answer". Scale: "Dozens to hundreds of agents per run". — [Claude Code docs: workflows](https://code.claude.com/docs/en/workflows)
- (a) Triggers: ask for a workflow, include the keyword `ultracode` in a prompt, or set `/effort ultracode`, which makes Claude plan a workflow "for each substantive task" so "each request uses more tokens and takes longer", and a subscription session "reaches a session or weekly limit sooner". With ultracode on, the large-workflow warning and the concurrent-subagent limit are not applied. — [Claude Code docs: workflows](https://code.claude.com/docs/en/workflows)
- (a) Cost and caps: "a single run can use meaningfully more tokens than working through the same task in conversation". A `Large workflow` warning appears above 25 agents or a projected 1.5 million tokens, but it "is advisory: it doesn't pause or limit the run". Hard caps: 16 concurrent agents by default (configurable up to 256), 1,000 agents per run, 4,096 items per fan-out call. Default size guideline is `medium` (fewer than 10 agents), or `small` (fewer than 5) on Pro; the guideline is advice, not a cap. Advice: try a small slice first. — [Claude Code docs: workflows](https://code.claude.com/docs/en/workflows)
- (a) Reliability mechanics and their catches: runs are resumable in the same session, but a failed agent mid fan-out causes every agent started after it to run again, including completed ones; stalled agents restart up to five times and their spent tokens still count; there is no mid-run user input; a run does not continue by itself if you exit the session. — [Claude Code docs: workflows](https://code.claude.com/docs/en/workflows)
- (a) Claimed quality benefit: a workflow can "have independent agents adversarially review each other's findings before they're reported ... so you get a more trustworthy result than a single pass". No measurement is given. — [Claude Code docs: workflows](https://code.claude.com/docs/en/workflows)

### Inferences
- Agent teams are the weakest-evidenced feature here relative to cost: experimental, several documented coordination failures, a vendor-stated multiple of token use, and no public benchmark of benefit. The best-supported uses are the non-coding ones Anthropic itself recommends starting with (parallel review, competing-hypothesis debugging).
- The documented fact that enabling teams changes ordinary delegation (teams forming unasked) is a practical reason to leave the flag off unless actively using them.
- Workflows look like the more defensible "many agents" option because the plan is a readable, rerunnable script with caps and a resume path, and because fan-out over independent items (per-file audits, migrations) is the task shape the independent research says benefits from multi-agent setups. But the cost exposure is large (up to 1,000 agents; warning is only advisory), and `/effort ultracode` in particular trades a lot of tokens for unmeasured gains.
- Anthropic's general principle from its 2025 research system still applies: the task's value must justify the token multiple.

### Gaps
- No independent or vendor benchmark shows agent teams or workflows improving coding outcomes per token or per hour.
- No published typical cost for a workflow run or for `/deep-research`.
- The "7x" figure is specific to teammates in plan mode; no figure is published for other configurations.
- The remaining 30,000 characters of the HN thread and the r/ClaudeAI and r/ClaudeCode communities were not sampled, so the volume and consistency of community complaints is only partly characterised.
- GitHub issues on anthropics/claude-code about teams and workflows were not reviewed.

## For each feature: known downsides and who benefits most

### Takeaway
Ranked by strength of evidence against cost and risk: hooks (a few deterministic ones), built-in subagent delegation, and local `/code-review` are low-cost and broadly useful; parallel sessions, headless or CI automation, managed Code Review and ultrareview are situational and pay off mainly for experienced developers and teams with good tests and review capacity; agent teams, always-on ultracode workflows, and treating `/security-review` as a security gate are the most likely to be overhyped on current evidence.

### Inferences
Suggested ranking for the report writer (my synthesis; opinion, not a sourced fact):
- **Must-use (low cost, consistent support):** one or two deterministic hooks (formatter after edits, notification on input needed, optionally a Stop-hook check); letting Claude use built-in Explore and Plan subagents; local `/code-review` before committing or opening a PR; plan mode plus a verification loop (outside this brief's scope but repeatedly named as the real multiplier by Cherny and Carlini).
- **Situational (clear value under conditions):** parallel sessions in worktrees or separate checkouts (needs independent tasks and review capacity); a few custom subagents (reviewer, test runner, verifier); headless `claude -p` and GitHub Actions (needs security ownership and budget caps); managed Code Review and ultrareview (needs budget, suits teams and large changes); `/batch` and scripted workflows for mechanical fan-out; cloud scheduled tasks for durable recurring jobs.
- **Most likely overhyped today:** agent teams (experimental, costly, no benchmark); `/effort ultracode` left on for routine work; large libraries of specialist subagents; relying on `/security-review` as a security control; `/loop` as an automation platform rather than a short-lived poller.
- By audience: a solo beginner gets most of the available value from defaults plus `/code-review` and should avoid parallelism and teams until they can confidently review one stream of output. An experienced solo developer gains most from hooks, a verification loop and two to five parallel sessions. Teams gain from committed hooks and settings (reviewed like code), CI review, and managed Code Review where human review is the bottleneck.
- A recurring pattern in the evidence: features that add determinism or verification (hooks, review, tests in the loop) have the most consistent support; features that add more agents have the most variable support and the clearest cost.

### Gaps
- Almost all benefit evidence is vendor-supplied or self-reported; I found no controlled study of any Claude Code feature in this list.
- Community sentiment (Reddit, GitHub issues) was sampled only through one Hacker News thread and search snippets, so claims about volume and consistency of complaints are tentative.
- Cost multiples for most features (subagents, workflows, `/batch`, ultracode) are not published; only agent teams (about 7x in plan mode) and review products ($5 to $25 and $15 to $25) have vendor figures.
- Several sources are more than a year old in a fast-moving product (Cognition and Ronacher June 2025, Semgrep Sept 2025, Willison Oct 2025); their specific descriptions of Claude Code behaviour may no longer hold.
