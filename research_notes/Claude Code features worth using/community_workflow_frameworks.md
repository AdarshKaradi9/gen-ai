# Community workflow frameworks and memory add-ons for Claude Code: Superpowers, spec-kit, BMAD-METHOD, SuperClaude, Ralph loop, claude-mem

Research date: 16 November 2026. All repository figures below were read from the live GitHub pages on that date.

**Evidence labels used on every finding**

- **(a)** maintainer claim or maintainer-published material (README, release notes, maintainer blog, vendor documentation about its own product). Where an (a) item is a checkable fact (licence, install command, release date) it is marked **FACT**; where it is a benefit claim it is marked **CLAIM**.
- **(b)** independent measurement or study (controlled or semi-controlled; quality noted individually, because several are small or vendor-run).
- **(c)** experienced-practitioner report (named engineer or organisation, hands-on).
- **(d)** anecdote (forum comment, issue-tracker report, single user story, press colour).

**Reading caveats that apply to the whole file**

- Pages were read through a fetch tool that summarises; short quotes are as the tool rendered them. Verify wording before quoting in a published report.
- GitHub release pages show day and month only; years were inferred from sequence and the 2026 page footer.
- GitHub star counts and marketplace install counts are recorded for context only and are not treated as evidence of usefulness.

### Inferences
- Maintenance is not the differentiator for five of the six: Superpowers, spec-kit, BMAD, claude-mem and the Anthropic-published ralph-loop plugin all shipped within the last five weeks. SuperClaude is the outlier (roughly eight months since a release, a promised v5 without a date, and a release note admitting earlier placeholder code).
- claude-mem has by far the largest runtime footprint (background worker, vector DB, nine hooks, second "observer" model). Superpowers and BMAD V7 are skills-only, which load on demand. SuperClaude is the largest always-available prompt surface (30 commands, 20 agents, 7 modes).
- Five claude-mem releases in five days at major version 15, with release notes dominated by reliability fixes, signals a project that is moving fast and breaking things rather than a stable dependency.

- I did not read the ralph-loop plugin's source or its README in `anthropics/claude-plugins-official`, only the marketplace listing.

## 2. Superpowers: imposed workflow, independent reports on quality versus overhead, official-marketplace status, Anthropic comment

### Takeaway
Superpowers imposes brainstorm → worktree → written plan → subagent-driven TDD with per-task review → branch finish. Named practitioners report better-considered designs and more confidence, but there is no independent controlled measurement of quality gain; the best-documented downsides are slowness, token burn in subagent mode, and process escalation on trivial changes (the most-commented open issue is about v7's brainstorming questions). It is in Anthropic's official marketplace with an "Anthropic verified" badge, but I found no statement from Anthropic staff about it.

### Cited Findings

**Workflow**
- (a) FACT: Seven steps: brainstorming (questions, then plays back understanding) → git worktree on a new branch → writing plans (tasks of "2-5 minutes each" with exact file paths and verification steps) → subagent-driven development (fresh subagent per task with review) or inline executing-plans (one final review) → TDD ("Deletes code written before tests") → code review between tasks ("Critical issues block progress") → finishing the branch (merge/PR/keep/discard) — [GitHub repo](https://github.com/obra/superpowers)
- (a) FACT: Since v5 (Mar 2026) subagent-driven development is the default where subagents exist, a subagent reviews the spec, and subagents use "the cheapest model capable of doing a given task". User CLAUDE.md/AGENTS.md take precedence over Superpowers' instructions — [Superpowers 5 post, 9 Mar 2026](https://blog.fsck.com/2026/03/09/superpowers-5/)

**Evidence for**
- (a) CLAIM: The author offers no benchmarks. Skills were "pressure tested" on subagents with scenarios; the first test round produced a "perfect score" that Vincent himself judged "less than useful" because subagents were being quizzed "like they were on a gameshow". v5's spec review "does seem to lead to a dramatic improvement in planning document quality" (hedged, unmeasured) — [Superpowers launch post, 9 Oct 2025](https://blog.fsck.com/2025/10/09/superpowers/); [Superpowers 5 post](https://blog.fsck.com/2026/03/09/superpowers-5/)
- (a) CLAIM: v6.4.2 release notes say the leaner `writing-plans` took "about a quarter of the time and a third of the tokens" of the previous version (self-measured, method not given; also an implicit admission that earlier plans were bloated) — [Releases page](https://github.com/obra/superpowers/releases)
- (c) Simon Willison (10 Oct 2025): "Jesse is one of the most creative users of coding agents (Claude Code in particular) that I know" and "way ahead of the curve". This is an endorsement of the author and approach on launch day, not a measured evaluation. He relays Vincent's statement that the core "pulls in one doc of fewer than 2k tokens" and that an end-to-end todo-app session used about 100k tokens — [simonwillison.net, 10 Oct 2025](https://simonwillison.net/2025/Oct/10/superpowers/)
- (c) Evan Schwartz (2 Apr 2026, states no connection to the authors): "Using Claude Code with Superpowers is so much more productive"; plans are easier to review as a sketch then a design doc; "I cannot recommend it enough." The post contains no numbers and discusses no downsides — [emschwartz.me, 2 Apr 2026](https://emschwartz.me/a-rave-review-of-superpowers-for-claude-code/)
- (b, weak: n=1, author sells competing tooling) In Felipe Fontoura's single-run comparison on a 24-line ledger task (claude-opus-5-5, Claude Code 2.1.296, headless), Superpowers 7.0.0 finished in 40 s for $0.33 API-equivalent and 0.23M input tokens, wrote 0 spec lines, and passed 13/13 acceptance checks but only 8 repo tests; Spec Kit took 473 s and $2.84. This suggests v7 sizes the process down for small work. There was no plain-Claude-Code baseline, and the author says "n=1 per tool, one model, one 24-line repo, one feature" — [felipefontoura.com, updated 29 Oct 2026](https://felipefontoura.com/articles/spec-driven-development-tools-compared/)

**Evidence against / overhead**
- (d) Issue #2530 "v7's brainstorm questions are rather annoying" (opened 16 Oct 2026, still open, about 37 thumbs-up, roughly 50 timeline entries, sentiment overwhelmingly negative). Users report irrelevant questions, reverting to 6.4.2, and "a one-line CSS change escalating to a full spec and plan" even on 7.0.x. Reporter: "please don't make us waste time and tokens with these questions." — [obra/superpowers issue #2530](https://github.com/obra/superpowers/issues/2530)
- (d) Other high-comment issues: #743 "Im seeing slowness in responses since using the skill" (open, 27 comments); #1152 a "relatively simple plan" with subagent-driven development "consumes full 5h token budget in a single run" on Codex (open, 15 comments); #895 "plans over-specify implementation, leaving no room for executor judgment" (closed Sep 2026, 24 comments); #809 "Long-running planning tasks timeout and fail" (open); #2386 "test-driven-development is not invoked for a plain 'add a function' request" (open) — [obra/superpowers issues filtered on "token", sorted by comments](https://github.com/obra/superpowers/issues?q=is%3Aissue+token+sort%3Acomments-desc)
- (d) Hacker News thread on the rave review (50 points, 25 comments, Apr 2026): of the comments addressing Superpowers directly about three were sceptical and two or three favourable. Quotes: d--b "I think Claude makes more mistakes when using superpowers than when not."; tao_oat "I do not like the separation of spec/plan" but self-review "has caught several things I would've missed"; raesene9 on install trust "it's like curl|bash but with added LLM agents..."; keheliya "ideally this should be natively implemented in cc." — [HN item 47623101](https://news.ycombinator.com/item?id=47623101)
- (d, secondary summary) An r/ClaudeCode thread "Are you guys still using the superpowers skill?" (June 2026, 150+ upvotes, 110+ comments) reportedly had a top-voted comment calling the framework "bloated" while praising the workflow, and another saying "Superpowers+Fable is a good way to waste a day of tokens"; defenders cited confidence and reviewability. I could not open Reddit; this is from a directory site with a commercial interest in skills listings — [mcp.directory, June 2026](https://mcp.directory/blog/superpowers-skill-worth-it-2026)
- (a) CLAIM (admission): visual brainstorming "can be token-intensive" — [Superpowers 5 post](https://blog.fsck.com/2026/03/09/superpowers-5/)
- (d) Hacker News has largely ignored the project itself: most direct submissions of the repo scored 1–4 points with 0 comments — [HN Algolia search](https://hn.algolia.com/api/v1/search?query=superpowers%20claude%20code&tags=story&hitsPerPage=15)

**Official marketplace and Anthropic comment**
- (a) FACT (Anthropic): Superpowers is listed on Claude Marketplace as "Anthropic verified" with 1,009,371 installs; the page does not say what verification covers — [claude.com/plugins/superpowers](https://claude.com/plugins/superpowers)
- (a) FACT (Anthropic): The official marketplace contains "Plugins Anthropic maintains, plus plugins from partners and other authors", and "Most of what it lists comes from partners and other authors rather than from Anthropic". Listing is therefore not authorship or a performance endorsement — [Claude Code docs: Anthropic's marketplaces](https://code.claude.com/docs/en/plugins/anthropic-marketplaces.md)
- (a) Maintainer statement, Oct–Nov 2026: 7.0.2 "should be much better, but Anthropic has been dragging their heels on importing it into the claude-plugins-official repo." The official-marketplace copy can therefore lag the author's own marketplace — [issue #2530](https://github.com/obra/superpowers/issues/2530)
- (a) FACT (Anthropic): For official-marketplace plugins the `/plugin` details pane shows token estimates ("Every turn" and "When invoked"), and `claude plugin details <name>` prints an "Always-on" token figure for any installed plugin. Users can measure Superpowers' context cost themselves — [Claude Code docs: Install and manage plugins](https://code.claude.com/docs/en/discover-plugins)

### Inferences
- The positive case rests entirely on (a) and (c) evidence: the author's own reasoning and two named practitioners' impressions. Nothing shows a measured quality gain over plain Claude Code with plan mode.
- The negative evidence is (d) but high-volume and consistent across the issue tracker, HN and the reported Reddit thread: the pattern is "the workflow ideas are good; the packaging is heavy; it over-processes small changes; subagent mode is expensive". The maintainer's own release notes (a quarter of the time and a third of the tokens after trimming plans; brainstorming retuned twice in three weeks) corroborate that overhead was real.
- The always-on context cost looks small (a bootstrap of under 2k tokens by the author's account); the cost is in what gets triggered (brainstorm rounds, long plans, a subagent plus reviewer per task), so the overhead is workflow time and output tokens rather than idle context.
- The Fontoura n=1 run hints that on a trivial task v7 can now be cheap, which conflicts with the "CSS change escalates to a full plan" reports. Behaviour on small tasks appears inconsistent and version-dependent.

### Gaps
- No statement by Anthropic staff about Superpowers was found. The only Anthropic signals are the marketplace listing and badge.
- A "12-session experiment" (about 14% fewer tokens overall, about 8% more on simple tasks) appeared in search snippets only; I could not locate or read the primary source (one candidate page returned HTTP 403), so it is not cited as evidence.
- The Reddit thread was not readable directly.
- No independent data on defect rates, rework, or time-to-merge with versus without Superpowers.

## 3. spec-kit and spec-driven development: evidence of improvement and substantive critiques

### Takeaway
The announcement offered no evidence. The strongest hands-on critiques (Böckeler at Thoughtworks, Eberhardt at Scott Logic, Zaninotto at Marmelab) agree that spec-kit produces large volumes of repetitive markdown, is overkill for small-to-medium work, and does not reliably make the agent follow the spec. The one benchmark with a no-spec control (a vendor blog, Oct 2026) shows a modest merge-rate edge for spec workflows on feature and data-pipeline tickets that is roughly within its own stated noise band, with spec-kit among the more expensive arms.

### Cited Findings

**Maintainer side**
- (a) CLAIM: SDD yields "less guesswork, fewer surprises, and higher-quality code"; useful for greenfield, features in existing systems, and legacy modernisation. The post contains no data, benchmarks or case studies, and calls Spec Kit "our experiment" — [GitHub blog, 2 Sep 2025](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)
- (a) FACT: The current README makes no quantitative effectiveness claims — [GitHub repo](https://github.com/github/spec-kit)

**Practitioner critiques**
- (c) Birgitta Böckeler (Thoughtworks Distinguished Engineer, 15 Oct 2025): spec-kit "created a LOT of markdown files for me to review", "repetitive" and "tedious to review"; for a 3–5 point feature it "felt like overkill for the size of the problem"; "I could have implemented the feature with 'plain' AI-assisted coding, and I would have felt much more in control"; she would "rather review code than all these markdown files"; despite templates and checklists "I frequently saw the agent ultimately not follow all the instructions", and sometimes it "went way overboard because it was too eagerly following instructions". On Kiro for a small bug: "like using a sledgehammer to crack a nut" (4 user stories, 16 acceptance criteria). She classes spec-kit as spec-first (a branch per spec), not spec-anchored, and closes with the *Verschlimmbesserung* question: "Are we making something worse in the attempt of making it better?" She compares spec-as-source to model-driven development and fears "Inflexibility *and* non-determinism" — [martinfowler.com, 15 Oct 2025](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- (c, with self-timed measurements) Colin Eberhardt (Scott Logic CTO, 26 Nov 2025; GitHub Copilot with Claude Sonnet 4.5): first feature via Spec Kit took a reported 33.5 min of agent time and about 3.5 h of review, producing 2,577 lines of markdown and 689 lines of code; second feature 23.5 min agent time, about 2 h review, 2,262 lines of markdown for about 300 lines of code. His usual iterative approach for the same goal: 8 min agent time, about 1,000 lines of code, 15 min review, 9 min testing. The Spec Kit output still had an obvious bug that the spec workflow gave no clean way to fix. Verdict: "For now, the fastest path is still iterative prompting and review, not industrialised specification pipelines." Note: his per-step table does not sum to his stated totals — [Scott Logic blog, 26 Nov 2025](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html)
- (c) François Zaninotto (Marmelab CEO, 12 Nov 2025): a "display the current date" feature via Spec-Kit produced "8 files and 1,300 lines of text"; problems listed are context blindness, "markdown madness", double code review ("review time doubles" because specs contain code), a false sense of security ("agents don't always follow the spec"; one marked a verification task done without writing tests), and "For large existing codebases, SDD is mostly unusable." — [Marmelab blog, 12 Nov 2025](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html)
- (c) Thoughtworks Technology Radar, technique "Spec-driven development": Assess (Nov 2025). "the workflows remain elaborate and opinionated"; tools "behave very differently depending on task size and type"; "some generate lengthy spec files that are hard to review"; "we may be relearning a bitter lesson" about handcrafting rules for AI — [Thoughtworks Radar](https://www.thoughtworks.com/radar/techniques/spec-driven-development)
- (c) Thoughtworks Radar, "GitHub Spec Kit": Assess (15 Apr 2026). More positive: teams mostly use it in brownfield systems; a useful "constitution" covers scope, domain context, versions, standards and repo structure; a spec → plan → tasks → coding → review lifecycle "surfaced issues earlier". Cautions: growing instruction sets "eventually led to context rot", plus "unnecessary defensive checks and verbose markdown output that added cognitive load"; customising templates helped; "Experienced engineers with strong clean-code and architecture practices get the most value." — [Thoughtworks Radar: GitHub Spec Kit](https://www.thoughtworks.com/radar/languages-and-frameworks/github-spec-kit)

**Measurements and studies**
- (b, vendor-run, not peer reviewed) Uvik Software benchmark (run 15 Oct 2026; claude-sonnet-5; Claude Code; 50 brownfield production Python tickets; blind senior review). Merge rate: OpenSpec 84%, Kiro 82%, BMAD 82%, Spec Kit 1.0 80%, no-spec control 72%, with a stated noise band of ±10 percentage points. Cost per merged ticket: Spec Kit $3.33, BMAD $4.23, control $2.43. Median time to merge: Spec Kit 44 min, BMAD 55 min, control 29 min. Review defects per merged ticket: Spec Kit 0.57, control 0.86. By type, features 80% versus 60% and data pipelines 80% versus 60% for Spec Kit versus control; bug fixes 80% versus 90%; refactors equal at 80%. On large tickets all spec arms merged 80% versus 50% for control. Conclusion: "use SDD selectively rather than on every ticket". Important limits: the control did **not** use plan mode (ticket text plus project instruction file only); one team; one model; Python only; the publisher sells engineering services; the run-per-arm design description was ambiguous in my read — [Uvik Software, updated 2 Nov 2026](https://uvik.net/blog/spec-driven-development-benchmark/)
- (b, weak: n=1) Fontoura comparison: Spec Kit 1.2.0 was "the most thorough and the most expensive" — 473 s, $2.84, 10 user prompts, 690 spec lines plus a 99-line constitution, 3.80M input tokens — for the same 13/13 result the lightest tool reached for $0.33. "The code converged." — [felipefontoura.com, 29 Oct 2026](https://felipefontoura.com/articles/spec-driven-development-tools-compared/)
- (b, qualitative) Agarwal et al., "Spec-Driven Development as Prescribed and as Practiced" (arXiv 2608.25202, Aug 2026; 21 practitioner interviews including 8 tool makers, Reddit analysis, 266 repositories from a 470,795-spec-file corpus): SDD is "used selectively, mainly for new features"; implementation detail in specs may help agents but makes specs prone to decay; spec-code checks happen at change completion, not continuously; reported benefits (more reliable agent behaviour) are practitioner perceptions and the study does not measure outcomes — [arXiv 2608.25202](https://arxiv.org/abs/2608.25202)

### Inferences
- The three independent hands-on critiques converge on the same failure mode from different stacks and dates, which makes "verbose markdown, heavy review burden, overkill for small work" the best-supported finding in this whole file.
- The Uvik result is the only pro-SDD measurement with a control, and its 8-point Spec Kit advantage is inside its own ±10-point noise band. The per-type pattern (helps multi-file features and data pipelines, does not help bug fixes and refactors) is plausible and matches practitioner intuition, but a control without plan mode overstates the gap against how experienced users actually run Claude Code.
- Among SDD tools, spec-kit is consistently the heaviest or second-heaviest on cost and markdown volume (Uvik, Fontoura, Eberhardt), while lighter alternatives (OpenSpec, Kiro) score the same or better. If someone wants SDD, spec-kit is not obviously the best implementation of it.
- Most of the sharpest critiques date from Oct–Nov 2025 against early spec-kit; the tool is now at v1.4.0 with extensions and customisable templates. The April 2026 Radar entry suggests the verbosity persisted but could be tamed by template customisation.

### Gaps
- No peer-reviewed controlled study of spec-kit versus plain agentic coding was found.
- No evidence on the long-run value of keeping specs (maintenance, onboarding); Uvik explicitly did not test it.
- A search snippet mentioned a Google workshop paper on spec-driven test generation (+9.8 points bug detection); I did not fetch it, and it concerns test generation rather than spec-kit.

## 4. BMAD-METHOD and SuperClaude: what they add, who uses them, criticisms, and independent evidence on persona/role prompts

### Takeaway
Both wrap Claude Code in a simulated team of role personas plus a process. For BMAD there is mixed practitioner evidence (disciplined output on large projects; days of planning and heavy token use on small ones) and one vendor benchmark showing it as the slowest and most expensive arm for the same merge rate as lighter tools. For SuperClaude I found **no independent hands-on evidence at all**; its "30-50% fewer tokens" and "2-3x faster" figures are maintainer claims without method. Research on persona prompting is mixed-to-negative: large studies find expert personas do not improve, and can reduce, accuracy on knowledge tasks, while one ACL 2025 paper found task-matched "personality" guidance improved code pass rates; nothing tests persona-based agent frameworks on agentic coding.

### Cited Findings

**BMAD**
- (a) CLAIM: BMad "keeps you in control while its agents and workflows make the important decisions explicit"; "Small changes go straight to build." No measured claims. V7 is recommended for "solo or small teams that can pivot as things will change before beta" — [GitHub repo](https://github.com/bmad-code-org/BMAD-METHOD)
- (c) Guillaume Lancrenon (8 Feb 2026): about two days of prompting through BMAD workflows for a simple macOS TODO app produced PROJECT.md, REQUIREMENTS.md, ROADMAP.md, ARCHITECTURE.md and epics/stories and "Zero lines of actual code." "For a small project, it's overkill." "I needed a TODO app, not a sprint ceremony." He switched to the lighter GSD — [guillim.github.io, 8 Feb 2026](https://guillim.github.io/ai/development/2026/02/08/bmad-method-disappointment.html)
- (d, compiled user reports) asantos2000 (10 Jan 2026) collects reports: one user burned about 230 million tokens in a week and needed a $200/month plan ("it burns up a lot of tokens"); one spent 9+ hours and the pipeline still marked a broken auth feature complete; another: "Honestly, this is taking me way longer than just doing it myself."; agents report success with bugs remaining; about two months to master. Positive counter-example: a developer on a large web app got "nearly 100 pages of documentation and ~350 unit tests" story by story where vibe-coding had failed, "more disciplined than what we were doing at work in a SAFe environment." The post also says v6's step-file architecture cut tokens per workflow run by about 74% (figures of unclear provenance) — [asantos2000 blog, 10 Jan 2026](https://asantos2000.github.io/blog/post-3/)
- (b, vendor-run) Uvik benchmark: BMAD 6.x merged 82% (versus 72% control; ±10 points noise) but was the costliest and slowest arm: $4.23 per merged ticket, 55 min median time to merge, 28 min spec overhead, 188 median spec lines, 43.9% of tokens spent in the spec phase, 12.2% spec drift — [Uvik Software, Nov 2026](https://uvik.net/blog/spec-driven-development-benchmark/)
- (b, weak: n=1) Fontoura: BMAD 6.12.2 was the cheapest of the three spec-writing tools on a tiny task (217 s, $1.89, 3 prompts, 88 spec lines, 13/13), but still about six times the cost of Superpowers for the same result — [felipefontoura.com, Oct 2026](https://felipefontoura.com/articles/spec-driven-development-tools-compared/)
- (c) Zaninotto groups BMad with spec-kit, Kiro and Tessl in his "waterfall strikes back" critique — [Marmelab, 12 Nov 2025](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html)
- (c, unnamed author) paddo.dev (28 Jan 2026): "It's waterfall with a language model bolted on"; BMAD's agents "form an org chart" compensating for human limits the model does not have; "Process overhead designed to make AI productive reduces AI effectiveness." Opinion essay with no measurements — [paddo.dev, 28 Jan 2026](https://paddo.dev/blog/the-framework-trap/)

**SuperClaude**
- (a) CLAIM: "For 2-3x faster execution and 30-50% fewer tokens, optionally install MCP servers"; Token-Efficiency mode gives "30-50% context savings". No benchmark or methodology is given — [GitHub repo](https://github.com/SuperClaude-Org/SuperClaude_Framework)
- (c, not hands-on; author runs a competing setup) Steven Gonsalvez: "I'm not going to validate those numbers (too many variables, too dependent on the specific task)"; "Every instruction in your CLAUDE.md eats context window."; "it's designed for someone else's workflow"; worth studying more than adopting. He discloses "I run my own setup with agents-in-a-box" — [dev.to](https://dev.to/stevengonsalvez/superclaude-the-claudemd-framework-that-went-viral-1ced)
- (a) FACT: The v4.3.0 release notes say placeholder code in ConfidenceChecker, intelligent_execute() and ReflexionPattern was only then replaced with working implementations — i.e. earlier releases advertised features that were stubs — [Releases page](https://github.com/SuperClaude-Org/SuperClaude_Framework/releases)

**Independent evidence on persona/role prompts**
- (b) Basil, Shapiro, Shapiro, Mollick, Mollick, Meincke (Wharton), "Playing Pretend: Expert Personas Don't Improve Factual Accuracy" (arXiv 2512.05858, 5 Dec 2025): six models on GPQA Diamond and MMLU-Pro; in-domain expert personas had no significant effect (one exception: Gemini 2.0 Flash); low-knowledge personas reduced accuracy; "no consistent benefit across models". These are multiple-choice knowledge benchmarks, not coding — [arXiv 2512.05858](https://arxiv.org/abs/2512.05858)
- (b) Hu, Rostami, Thomason (USC), "Expert Personas Improve LLM Alignment but Damage Accuracy" (arXiv 2603.18507, 19 Mar 2026). As reported by The Register (24 Mar 2026, headline "Telling an AI model that it's an expert programmer makes it a worse programmer"): on MMLU the expert persona scored 68.0% versus 71.6% for the base model; personas helped alignment-style tasks (a "Safety Monitor" persona raised JailbreakBench refusals from 53.2% to 70.9%); author Hu: "if you care more about accuracy and facts, do not add anything, just send the query." The arXiv abstract itself does not mention coding; the coding framing comes from the press article — [arXiv 2603.18507](https://arxiv.org/abs/2603.18507); [The Register, 24 Mar 2026](https://www.theregister.com/2026/03/24/ai_models_persona_prompting/)
- (b, contrary result) Guo et al., "Personality-Guided Code Generation Using Large Language Models" (ACL 2025 main track, arXiv 2411.00006): task-matched personality guidance improved pass rates in 23 of 28 model–dataset combinations, by more than 5% in 11 and more than 10% in 5 (maximum 12.9%). This is single-shot function generation on models of the 2024 generation, not agentic work — [arXiv 2411.00006](https://arxiv.org/abs/2411.00006)
- (b) Khojah et al., "The Impact of Prompt Programming on Function-Level Code Generation" (arXiv 2412.20545, revised Jul 2025): persona was one of five techniques tested on GPT-4o, Llama3 and Mistral; combining techniques did not necessarily help, and there was a trade-off between correctness and quality. Persona-specific numbers are not in the abstract I read — [arXiv 2412.20545](https://arxiv.org/abs/2412.20545)

### Inferences
- The value in BMAD, where users report any, appears to come from forced decomposition and documentation (stories, tests, architecture records), not from the personas themselves. Persona research gives no reason to expect that naming an agent "Architect" improves the code, and some reason to expect a small accuracy cost on recall-heavy work.
- BMAD's cost profile is the worst-evidenced-for-benefit in the SDD group: equal merge rate to lighter tools at the highest cost and time (Uvik), and a documented failure mode of days of planning for trivial projects. Its V7 rewrite as on-demand skills with a "small changes go straight to build" path is an implicit acknowledgement.
- SuperClaude is the clearest case in this file where the **only** evidence of benefit is the maintainer's own promotion: unsourced percentage claims, no independent hands-on review found, a stale release cadence, and a release note admitting stubbed features.
- Persona findings should be applied cautiously: the negative studies are on multiple-choice knowledge benchmarks, the positive one on single-function generation; none evaluates multi-agent role frameworks on real repositories.

### Gaps
- No hands-on independent review of SuperClaude with measurements was found; search results were dominated by promotional or directory pages (snippet-level only, not cited).
- No study isolating the effect of role personas inside an agentic coding harness (for example BMAD with and without persona text).
- A rebuttal paper to the Wharton persona study (arXiv 2603.20225) surfaced in search but was not fetched.
- "Who uses them" could not be established beyond anecdote; no adoption surveys were found. A search snippet (not fetched) said the Thoughtworks Radar's OpenSpec entry names BMAD as a "heavier alternative".

## 5. Ralph loop: the technique, actual results, cost, and risks of unattended looping

### Takeaway
Ralph is a deliberately dumb outer loop that restarts a fresh agent on the same prompt, one task per iteration, with state kept in files and git. Documented results are real but narrow: ports and greenfield bootstraps that reach roughly 90% and need human finishing, at about $10 per agent-hour. Its inventor says not to use it on existing codebases, and experienced users say Anthropic's stop-hook plugin loses the technique's key property (fresh context per iteration).

### Cited Findings

**Technique**
- (a) FACT/CLAIM (Huntley, 14 Jul 2025): "In its purest form, Ralph is a Bash loop"; one task per loop, driven by PROMPT.md, specs and a `fix_plan.md`, with the prompt tuned by watching failures. "the technique is deterministically bad in an undeterministic world." — [ghuntley.com/ralph](https://ghuntley.com/ralph/)
- (c) Dex Horthy (HumanLayer, 6 Jan 2026): the point of Ralph is to "carve off small bits of work into independent context windows" — [HumanLayer blog, 6 Jan 2026](https://www.humanlayer.dev/blog/brief-history-of-ralph)

**Results**
- (a) CLAIM: A "$50k USD contract" was delivered for "$297 USD" using Amp; the evidence is a shared iMessage screenshot from a third party, not verifiable — [ghuntley.com/ralph](https://ghuntley.com/ralph/)
- (a) CLAIM: Ralph built CURSED, a new programming language; Huntley describes its repo as "full of garbage, temporary files, and binaries" — [ghuntley.com/ralph](https://ghuntley.com/ralph/). (c) Horthy records CURSED launching in Sep 2025, written in C, then Rust, then Zig, with a standard library and stage-2 compiler — [HumanLayer blog](https://www.humanlayer.dev/blog/brief-history-of-ralph)
- (c, with cost figures) RepoMirror team at the YC Agents hackathon (about Aug 2025): Claude Code headless in a while loop overnight ported six codebases (e.g. Browser Use from Python to TypeScript, Vercel AI SDK from TypeScript to Python). "We spent a little less than $800 on inference"; "Each Sonnet agent costs about $10.50/hour to run overnight"; "~1100 commits". Problems: output needed human work to go from about 90% to 100%; agents claimed completion when demos did not work; one agent added unrequested Flask/FastAPI integrations; one used `pkill` to stop itself when stuck; a Claude-"improved" 1,500-word prompt made the agent slower and worse than the original 103-word prompt — [repomirror.md](https://github.com/repomirrorhq/repomirror/blob/main/repomirror.md)
- (c) Horthy's own trials: a productivity app came out "meh" because he had not read the specs or code; a six-hour refactor against a written standards doc worked but produced a change set too large to merge without conflicts; he now runs small Ralph-style loops overnight on a cron. "if you are iterating/exploring, you probably don't want ralph in the first place" — [HumanLayer blog](https://www.humanlayer.dev/blog/brief-history-of-ralph)
- (d, press) Huntley puts the cost at "about US $10 of compute and/or SaaS resources each hour" and describes cloning commercial products from reverse-engineered material; the article quotes no outside critics, says Boris Cherny "has said he uses Ralph", and carries no Anthropic statement — [The Register, 27 Jan 2026](https://www.theregister.com/2026/01/27/ralph_wiggum_claude_loops/)
- (d, press) A community member's 14-hour autonomous session reportedly upgraded a codebase from React v16 to v19; Matt Pocock recommends strong feedback loops (TypeScript, unit tests). The article attributes formalising the plugin to Boris Cherny and carries a correction note about him; its own dates for the plugin are inconsistent (late 2025 versus summer 2025) — [VentureBeat, 6 Jan 2026](https://venturebeat.com/ai/how-ralph-wiggum-went-from-the-simpsons-to-the-biggest-name-in-ai-right-now/)

**Risks and limits**
- (a) Huntley's own warnings: "This nondeterminism is the Achilles' heel of Ralph."; "Claude has the inherent bias to do minimal and placeholder implementations."; you may "wake up to a broken codebase that doesn't compile from time to time"; without static analysis "a bonfire of outcomes"; "There's no way in heck would I use Ralph in an existing code base."; "This works best as a technique for bootstrapping Greenfield, with the expectation you'll get 90% done with it."; senior engineering oversight is still required — [ghuntley.com/ralph](https://ghuntley.com/ralph/)
- (d, press) Runaway cost: a loop that runs until success can burn tokens on an impossible task, hence the `--max-iterations` recommendation. Security: Ralph commonly runs with `--dangerously-skip-permissions`, so commentators advise disposable sandboxes or VMs — [VentureBeat, 6 Jan 2026](https://venturebeat.com/ai/how-ralph-wiggum-went-from-the-simpsons-to-the-biggest-name-in-ai-right-now/)
- (c) Horthy on the Anthropic plugin (Dec 2025 release): "it dies in cryptic ways unless you have `--dangerously-skip-permissions`"; it "adds an opaque stop hook for all claude sessions in a directory until you disable it"; state is tracked in a markdown file whose deletion can break Claude in that repo; and conceptually it "misses the key point of ralph" — [HumanLayer blog, 6 Jan 2026](https://www.humanlayer.dev/blog/brief-history-of-ralph)
- (a) FACT (Anthropic): The plugin page recommends it for "well-defined projects with clear success criteria" and greenfield work with automated verification; the only stated controls are the iteration limit and completion promise; the page lists no safety warnings — [claude.com/plugins/ralph-loop](https://claude.com/plugins/ralph-loop)
- (d) HN interest was modest and partly critical (e.g. "What Ralph Wiggum loops are missing", 25 points, 25 comments, Jan 2026) — [HN Algolia search](https://hn.algolia.com/api/v1/search?query=ralph%20wiggum%20loop&tags=story&hitsPerPage=10)

### Inferences
- Ralph is a technique, not a product; it costs nothing to try and has the most concrete cost data of anything here (about $10/hour per Sonnet-class agent in 2025). Its documented wins share three properties: a clear external oracle (an existing codebase to port, tests, a compiler), greenfield or isolated scope, and tolerance for throwing work away.
- The Anthropic `ralph-loop` plugin and the original technique are not equivalent: the plugin keeps one session alive via a Stop hook, whereas the bash loop gives every iteration a fresh context. Practitioners who value Ralph prefer the bash loop (or headless `claude -p` in a loop); the plugin is the convenient, lower-ceiling variant.
- The headline "$50k contract for $297" is unverified author promotion and should not be used as evidence. The repomirror figures are the usable cost benchmark.
- The main risks are operational, not conceptual: unattended permission bypass, unbounded spend, false "done" claims, scope creep, and unmergeable giant diffs.

### Gaps
- No systematic measurement of Ralph output quality (defect rates, proportion of runs that converge) exists in what I found; all results are case reports.
- I did not find Huntley's own written comments on the Anthropic plugin (a Jan 2026 video with Horthy reportedly covers it; not viewed).
- Cost figures date from 2025 models; current per-hour costs with 2026 models were not found.
- No Anthropic statement on safe use of ralph-loop beyond the listing page was found.

## 6. claude-mem: what it does, comparison with built-in auto memory and CLAUDE.md, overhead, privacy/licence/reliability concerns

### Takeaway
claude-mem records every tool call via hooks, has a second "observer" model compress them into observations, and injects an index at session start. Claude Code now ships auto memory on by default, which covers the basic "remember across sessions" need with no extra processes or model calls. claude-mem's "~10x token savings" claim was withdrawn by the maintainer in November 2026 as "not a measured saving", and its tracker documents quota drain by the observer, leaked processes, a 312 GB memory incident, and an installer that uploaded 30 days of prompts to cmem.ai without opt-in until v15.8.3. The AGPL concern is obsolete (now Apache-2.0).

### Cited Findings

**How it works**
- (a) FACT: Hooks pass each tool call to a local worker; an observer agent turns activity into short observations and a session summary; the next session gets "a compact index of relevant observations" and fetches details on demand through MCP tools. The observer can run on claude-mem's own observer service, an OpenRouter or Gemini key, or the user's Anthropic plan. Content inside `<private>` tags is not stored — [GitHub repo](https://github.com/thedotmack/claude-mem)
- (a) CLAIM: Index rows cost roughly "~50-100 tokens/result" and full details "~500-1,000 tokens/result"; with the hosted observer, "up to 100% more usage from your plan" (no independent measurement) — [GitHub repo](https://github.com/thedotmack/claude-mem)

**Built-in alternative**
- (a) FACT (Anthropic): Claude Code has two built-in mechanisms loaded every session: CLAUDE.md (written by the user) and auto memory (notes "Claude writes itself based on your corrections and preferences"). "Auto memory is on by default in local sessions." It is stored per repository at `~/.claude/projects/<project>/memory/` as a `MEMORY.md` index plus topic files; "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first, are loaded at the start of every conversation"; it is machine-local; it can be toggled in `/memory` or disabled with `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- (a) FACT (Anthropic): "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- (c, vendor blog, not hands-on testing) Augment Code positions claude-mem as automatic capture versus hand-maintained static instructions and repeats "Roughly 10x token savings" without method; it reports no reliability testing. The article predates the maintainer's withdrawal of that figure — [Augment Code blog, 11 May 2026](https://www.augmentcode.com/learn/claude-mem-74k-stars-agent-memory)

**Token and resource overhead**
- (d, detailed issue with measurements) Issue #5023 (v15.0.1, opened 23 Oct 2026, closed 12 Nov): with the default 400,000-character observer budget, observer turns reached about 100,155 tokens each; 677 observer responses in one hour; 7 consecutive condense calls of about 67.5K input tokens each with zero cache reads for one 210 KB file; the weekly subscription meter moved from 0% to 2% while the user was idle; observer usage was invisible in transcripts. The maintainer accepted the report and lowered the default to 100,000 characters — [claude-mem issue #5023](https://github.com/thedotmack/claude-mem/issues/5023); default change confirmed in [Releases page](https://github.com/thedotmack/claude-mem/releases)
- (d) Other closed issues: #1742 background observer sessions used "excessive tokens" ($17+ in 3 hours); #1090 worker spawned hundreds of leaked Claude CLI processes "consuming massive API tokens"; #3839 condense step sent uncapped payloads including base64 screenshots, 82% of calls discarded after timeout; #761 request to disable Chroma because of RAM use and zombie processes — [claude-mem issues filtered on "token usage"](https://github.com/thedotmack/claude-mem/issues?q=is%3Aissue+token+usage+sort%3Acomments-desc)
- (d → a) Issue #4138 (Sep–Nov 2026): the README's "~10x token savings" was challenged as unverifiable; on a 91k-observation store, a multi-word query returned 3 results with the shipped exact-phrase search versus 76 with AND matching, and natural-language sentences returned 0. Maintainer: the figure "isn't a measured recall number, and the README should say so plainly"; it was reworded to "a size ratio, not a measured saving". No recall baseline was merged — [claude-mem issue #4138](https://github.com/thedotmack/claude-mem/issues/4138)

**Reliability**
- (a) FACT (release notes, Nov 2026): v15.18.5 fixed a bug where a corrupt Chroma collection queued about 19 drops at once, pushing chroma-mcp to "a 312 GB memory footprint" and stalling a 32 GB Mac; v15.18.3 fixed Codex silently disabling all claude-mem hooks after each update so that "sessions stopped being saved with no message"; v15.18.2 fixed Gemini CLI hooks failing on Windows on every event since 15.18.0; v15.18.1 capped retries after one report measured 104,869 calls — [Releases page](https://github.com/thedotmack/claude-mem/releases)
- (d) Most-commented issues include worker start failures on port 37777 (#380, #197), a DB migration miss that broke the plugin (#121), a version-mismatch kill loop (#3857, #3940), "why does this leave CLAUDE.md files literally all over?" (#609) with related reports of CLAUDE.md files created in subdirectories and shadowing Python packages (#641, #697), "Can't open claude code when I install this plugin" (#303), and open architecture plans for child-process ownership ("every process the worker spawns dies with the worker", #3602) and queue-state integrity (#3609) — [claude-mem issues sorted by comments](https://github.com/thedotmack/claude-mem/issues?q=is%3Aissue+sort%3Acomments-desc)

**Privacy**
- (d, confirmed by maintainer's fix) Issue #5176 (opened 29 Oct 2026, closed 10 Nov): interactive `npx claude-mem install` (installer v15.2.0+) opened a setup page that read local chat histories from five tools (Claude Code, Codex, Gemini CLI, Antigravity CLI, OpenCode) and uploaded the last 30 days of prompts, with session IDs, project names and folder paths, to cmem.ai on page load with no opt-in; per the reporter, cmem.ai confirmed the prompts were sent to a DeepSeek model via OpenRouter without zero-data-retention settings. The privacy policy said "Nothing leaves your device unless you explicitly turn on cloud sync." Maintainer: "Fixed by #5220 ... released in v15.8.3"; "Nothing is uploaded until you choose **Discover My Work, Rules & Focus**". He did not answer questions about purpose, downstream providers or retention, and referred already-uploaded prompts to cmem.ai. A second commenter corroborated from source review — [claude-mem issue #5176](https://github.com/thedotmack/claude-mem/issues/5176)
- (a) FACT: Anonymous usage analytics are on by default; cloud sync is opt-in — [GitHub repo](https://github.com/thedotmack/claude-mem)

### Inferences
- For a single developer on one machine, built-in auto memory plus a concise CLAUDE.md delivers the core benefit (persistent learned preferences and project facts) with zero added processes, zero extra model calls and no third-party data flow. claude-mem's distinct additions are full activity capture, semantic search over history, cross-agent memory and a viewer.
- claude-mem's cost is not mainly injected context; it is a second model continuously re-reading activity (the observer), which can consume the same subscription quota as the user's work and was invisible in transcripts until November 2026.
- The combination of an unmeasured headline claim (now withdrawn), a no-consent prompt upload that contradicted the stated privacy policy, default-on analytics, a commercial cloud tier and an endorsed crypto token means trust, not licence, is now the main adoption concern. The Apache-2.0 change removes the earlier AGPL obstacle for companies.
- No source measures whether claude-mem's recalled context improves coding outcomes; the only retrieval-quality datum (issue #4138) showed poor recall before a fix.

### Gaps
- No independent benchmark of claude-mem versus auto memory (recall quality, task success, tokens) was found.
- HN discussion of claude-mem was negligible (the privacy issue submission had 3 points, 0 comments — [HN Algolia search](https://hn.algolia.com/api/v1/search?query=claude-mem&tags=story&hitsPerPage=10)), so community scrutiny outside the issue tracker is thin.
- I did not verify the upload behaviour or the fix in source code; the account relies on the issue thread and the maintainer's confirmation of a fix.
- The always-injected SessionStart context size in tokens for a typical project was not found in a measured form.

## 7. Across all of them: controlled comparisons against plain Claude Code with a good CLAUDE.md and plan mode; what experienced engineers say about heavy frameworks versus minimal setups

### Takeaway
**No controlled comparison of any of these frameworks against plain Claude Code with plan mode exists in what I could find.** The nearest items are a vendor benchmark whose control lacked plan mode, an n=1 four-way comparison with no baseline, and an unexecuted benchmark proposal. Adjacent research (ETH's AGENTS.md study) and Anthropic's own guidance both point toward less always-on instruction, and the creator of Claude Code describes his own setup as "surprisingly vanilla".

### Cited Findings
- (b, vendor-run) Uvik (Oct 2026) is the only study found with a no-spec control: 72% merge for control versus 80–84% for spec frameworks (noise ±10 points), control fastest (29 min) and near-cheapest ($2.43 per merged ticket). Its control was explicitly not plan mode; plan mode is listed as a future "light arm" — [Uvik Software](https://uvik.net/blog/spec-driven-development-benchmark/)
- (b, weak: n=1) Fontoura (Oct 2026): four frameworks, one run each, no plain baseline; code quality "within one item of each other" with an 8.6-fold cost spread ($0.33 to $2.84). "The code converged." — [felipefontoura.com](https://felipefontoura.com/articles/spec-driven-development-tools-compared/)
- (d) A GitHub issue (23 Oct 2026) proposing a reproducible n=3 head-to-head notes the Fontoura run "cannot be reproduced exactly" (fixture and scoring unpublished, checklist written after two of four runs); the proposed benchmark is not yet run and also omits a plain baseline; its author maintains a competing tool — [petruseugene/full-development-cycle issue #12](https://github.com/petruseugene/full-development-cycle/issues/12)
- (b) Gloaguen et al. (ETH Zurich), "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?" (arXiv 2602.11988, Feb 2026, revised Sep 2026): context files generally did not improve task success, for both LLM-generated and developer-written files, across models and agents, while raising inference cost by over 20% on average; agents did follow the instructions; repository overviews were not helpful; context files are useful for specifying non-standard practices — [arXiv 2602.11988](https://arxiv.org/abs/2602.11988)
- (a, Anthropic guidance) Keep CLAUDE.md under about 200 lines because "Longer files consume more context and reduce adherence"; CLAUDE.md and memory are "context, not enforced configuration" — use a PreToolUse hook to actually block actions — [Claude Code docs: memory](https://code.claude.com/docs/en/memory)
- (c, quoted via a secondary blog; primary X thread not opened) Boris Cherny, creator of Claude Code, 3 Jan 2026: "My setup might be surprisingly vanilla! Claude Code works great out of the box, so I personally don't customize it much."; "A good plan is really important!"; "give Claude a way to verify its work. If Claude has that feedback loop, it will 2-3x the quality of the final result." The blog paraphrases that most of his sessions start in plan mode and that the team shares one CLAUDE.md that accumulates corrections — [paddo.dev, 5 Jan 2026](https://paddo.dev/blog/how-boris-uses-claude-code)
- (c) Böckeler: "an effective SDD tool would at the very least have to provide flexibility for a few different core workflows"; she is "very skeptical that lots of up-front spec design is a good idea" — [martinfowler.com, 15 Oct 2025](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- (c) Thoughtworks Radar (Apr 2026): the industry is splitting into "teams relying on increasingly capable coding agents with minimal structure, and teams preferring defined workflows"; one team fixed context rot by moving guidance into on-demand skills — [Thoughtworks Radar: GitHub Spec Kit](https://www.thoughtworks.com/radar/languages-and-frameworks/github-spec-kit)
- (c, unnamed author; opinion) paddo.dev "The Framework Trap" (28 Jan 2026) recommends a CLAUDE.md under 300 lines, built-in plan mode, verification loops (tests, type checkers, linters) and path-scoped rules: "The model is the framework."; "they feel productive while adding friction." — [paddo.dev, 28 Jan 2026](https://paddo.dev/blog/the-framework-trap/)
- (c) RepoMirror: a 103-word prompt outperformed a Claude-expanded 1,500-word prompt in their loops — [repomirror.md](https://github.com/repomirrorhq/repomirror/blob/main/repomirror.md)
- (d) HN commenters on the Superpowers review largely debated plan mode itself; several preferred plain Claude Code or wanted the workflow "natively implemented" — [HN item 47623101](https://news.ycombinator.com/item?id=47623101)

### Inferences
- The burden of proof is unmet for every framework here: none has shown, in a controlled way, better outcomes than plan mode plus a short CLAUDE.md plus a verification loop. The available measurements are consistent with "structure helps somewhat on larger multi-file feature work, costs time and tokens everywhere, and the lightest structure does as well as the heaviest".
- Two independent lines agree that more always-on instruction is not better: the ETH study (no success gain, +20% cost) and Anthropic's own "reduce adherence" warning. This cuts hardest against SuperClaude-style and BMAD v6-style installs and least against on-demand skills (Superpowers, BMAD V7), which load only when triggered.
- The capabilities these frameworks pioneered (plan-before-code, subagents, skills, a loop plugin, auto memory) are now native to Claude Code, which narrows the marginal benefit of each add-on over time. Evidence older than about six months probably overstates the gap.
- **Tentative evidence-based tiering (inference, for the report writer):**
  - *Must-use:* none. No add-on has evidence strong enough for that label.
  - *Situational, best supported:* **Superpowers** (named-practitioner support, active maintenance, on-demand skills, official-marketplace distribution; skip or bypass for small changes) and the **Ralph technique** (free, well-characterised costs and limits; greenfield/ports with strong tests and a sandbox only).
  - *Situational, narrow:* **spec-kit** (larger features or brownfield teams with experienced engineers who will customise templates; lighter SDD tools match it at lower cost) and **BMAD** (large greenfield efforts that want documentation and ceremony; poor fit for solo or small work).
  - *Overhyped relative to evidence:* **SuperClaude** (maintainer-only claims, stale releases, persona-centred design with no supporting research) and **claude-mem** (headline saving withdrawn, documented quota drain and privacy incident, built-in auto memory covers the base case).

### Gaps
- No controlled benchmark with a "plain Claude Code + plan mode + good CLAUDE.md" arm was found for any of the six tools. This is the central evidence gap.
- No peer-reviewed study evaluates Superpowers, BMAD, SuperClaude, Ralph or claude-mem at all.
- Boris Cherny's statements were read via a blog reproduction, not the original X thread.
- Reddit (r/ClaudeAI, r/ClaudeCode) could not be fetched directly; community signal there is represented only by one secondary summary.

## 8. For each: who benefits most (solo beginner, experienced developer, team) and when to skip it

### Takeaway
Fit depends on task size and on whether the user already plans and verifies by habit: the frameworks add most for people or teams who lack a disciplined process on multi-file work, and add mostly friction for experienced developers on small or exploratory changes.

### Cited Findings
- **Superpowers.** (c) Schwartz values it because Claude is less likely to jump into implementation and plans are reviewable in stages — [emschwartz.me](https://emschwartz.me/a-rave-review-of-superpowers-for-claude-code/). (d) Users report trivial changes escalating to a full spec and plan, and heavy token use in subagent mode — [issue #2530](https://github.com/obra/superpowers/issues/2530); [issues list](https://github.com/obra/superpowers/issues?q=is%3Aissue+token+sort%3Acomments-desc). (d, secondary; commercially interested site) One write-up recommends the full plugin for newcomers and teams needing consistency, individual skills for experienced solo developers, and skipping when token budgets are tight — [mcp.directory](https://mcp.directory/blog/superpowers-skill-worth-it-2026)
- **spec-kit.** (c) "Experienced engineers with strong clean-code and architecture practices get the most value"; mostly brownfield teams — [Thoughtworks Radar: GitHub Spec Kit](https://www.thoughtworks.com/radar/languages-and-frameworks/github-spec-kit). (b, vendor-run) Use a full spec when a change touches three or more files, has four or more acceptance criteria, or alters a schema or public API; bug fixes, refactors and test-writing "often did not justify" it — [Uvik Software](https://uvik.net/blog/spec-driven-development-benchmark/). (c) Overkill for a 3–5 point feature; tools assume the developer does product analysis without saying so — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html). (c) "For large existing codebases, SDD is mostly unusable." (conflicts with the Radar's brownfield reports) — [Marmelab](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html); contradicted by [Thoughtworks Radar: GitHub Spec Kit](https://www.thoughtworks.com/radar/languages-and-frameworks/github-spec-kit)
- **BMAD.** (a) V7 preview is aimed at "solo or small teams that can pivot"; the Method module targets "new prototypes to established codebases" — [GitHub repo](https://github.com/bmad-code-org/BMAD-METHOD). (c) Overkill for a small project (two days, no code) — [guillim.github.io](https://guillim.github.io/ai/development/2026/02/08/bmad-method-disappointment.html). (d) Best reported fit is a large application delivered story by story with heavy documentation and tests; about two months to master — [asantos2000 blog](https://asantos2000.github.io/blog/post-3/)
- **SuperClaude.** (c) "a reasonable starting point for newcomers"; experienced users with their own workflow "will get more value from studying it than adopting it wholesale" — [dev.to, Gonsalvez](https://dev.to/stevengonsalvez/superclaude-the-claudemd-framework-that-went-viral-1ced)
- **Ralph.** (a) Greenfield bootstrapping to about 90%; not for existing codebases; needs senior oversight — [ghuntley.com/ralph](https://ghuntley.com/ralph/). (c) Not for iterating or exploring; needs a known end state and a way to test it; good for refactors against a written standard and small scheduled changes — [HumanLayer blog](https://www.humanlayer.dev/blog/brief-history-of-ralph). (a, Anthropic) "well-defined projects with clear success criteria" with automated verification — [claude.com/plugins/ralph-loop](https://claude.com/plugins/ralph-loop)
- **claude-mem.** (c, vendor blog) "Install it if you run multi-session AI coding workflows." — [Augment Code blog](https://www.augmentcode.com/learn/claude-mem-74k-stars-agent-memory). (a, Anthropic) Built-in auto memory is on by default, per repository and machine-local — [Claude Code docs: memory](https://code.claude.com/docs/en/memory). (d) Subscription-quota drain and the no-opt-in upload argue against use on client or regulated code without auditing the current version — [issue #5023](https://github.com/thedotmack/claude-mem/issues/5023); [issue #5176](https://github.com/thedotmack/claude-mem/issues/5176)

### Inferences
- **Solo beginner:** most likely to benefit from Superpowers, because it supplies the plan/test/review discipline they lack and is one command from the official marketplace; expect slower sessions. BMAD and spec-kit will bury a beginner in documents; Ralph unattended is risky without the judgement to audit its output; claude-mem adds failure modes a beginner cannot debug, and auto memory is already on.
- **Experienced solo developer:** the evidence favours a minimal setup (plan mode, short CLAUDE.md, tests as the verification loop), borrowing individual ideas or skills from Superpowers and using a Ralph-style bash loop for well-specified ports, migrations and greenfield bootstraps in a sandbox. Skip SuperClaude and BMAD; skip claude-mem unless searchable cross-session history is a concrete need.
- **Team:** spec-kit (or a lighter SDD tool) has the most plausible team value, since specs and a constitution can become shared, reviewable artefacts, provided the team customises templates and applies it selectively to larger features. BMAD is defensible only where heavy documentation is itself a deliverable. Superpowers can standardise individual practice, but the official-marketplace copy may lag the author's releases.
- **Skip rules common to all:** one-line fixes, bug fixes with a failing test, refactors with green tests, exploratory or UI-tweaking work, and any situation with a tight token or subscription budget.

### Gaps
- No source segments outcomes by user experience level; the fit guidance above is inference from practitioner reports and from one vendor benchmark that noted engineers had unequal framework experience.
- Team-scale evidence (for example, a named company's before-and-after metrics from adopting spec-kit or BMAD) was not found.
- No evidence on how any of these behave with the newest 2026 models specifically, beyond anecdotes that newer models need the scaffolding less.
