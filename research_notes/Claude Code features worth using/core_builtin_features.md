## 1. What does Anthropic itself recommend as the highest-leverage practices, and which features does it put first?

### Takeaway
As of November 2026 Anthropic's best-practices page leads with three things: tell Claude what it cannot see (specific prompt, short CLAUDE.md, skills for procedures), give it a runnable check to verify its own work, and move must-never-fail rules out of prompts into hooks/permissions. Plan mode is not mentioned on that page at all, aggressive context management is explicitly demoted to "advice you can stop following", and `/clear` between tasks is the one context habit it still endorses.

### Cited Findings
- **[a]** The page's own summary line is: "Get more out of Claude Code: tell Claude what it can't see, give it a check to run, and enforce the rules that can't have exceptions." Section order: (1) deterministic vs non-deterministic instructions, (2) tell Claude what it can't see (specific prompt, brainstorm/spec first, keep CLAUDE.md short, path-scoped rules, skills, tool connections), (3) give Claude a check to run, (4) enforce rules with hooks/permissions, (5) change a default, (6) steer the session, (7) run unattended, (8) what you can stop doing. — [Claude Code docs: Best practices](https://code.claude.com/docs/en/best-practices) (fetched 2026-11-16; undated living page)
- **[a]** Anthropic's baseline claim is that little setup is needed: "Claude Code is built in a way that, in most cases, your first plain prompt in a fresh session already does the right thing, without any setup on your part." — [Best practices](https://code.claude.com/docs/en/best-practices)
- **[a]** On CLAUDE.md: "Only write down what Claude can't find by reading the repo, or what it would otherwise spend time rediscovering every session." and "every line in it takes a little of Claude's attention on *every* task, whether it's relevant or not." Recommended contents: verification commands, misleading code areas, decisions not in the repo, "Anything you've had to correct twice already". — [Best practices](https://code.claude.com/docs/en/best-practices)
- **[a]** Verification is given the strongest wording: "If your repo already has one of these [checks], the single most useful line in your `CLAUDE.md` is the command that runs it." — [Best practices](https://code.claude.com/docs/en/best-practices)
- **[a]** On `/init`: "`/init` generates a starting version from your codebase. From there the work is mostly removing lines. The memory guide recommends staying under 200." `/doctor` "suggests cuts for anything Claude can already work out from the code". — [Best practices](https://code.claude.com/docs/en/best-practices)
- **[a]** CLAUDE.md and skills are non-deterministic: "there's no *guarantee* that it'll follow your instructions"; "`CLAUDE.md` is for guidelines, and Claude is allowed to decide a guideline doesn't apply"; "If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook." — [Best practices](https://code.claude.com/docs/en/best-practices)
- **[a]** Skills are positioned as the place for team procedures and as cheaper than CLAUDE.md: "Skills are also lighter on context than `CLAUDE.md` for this kind of thing... A long release procedure sitting in a skill doesn't weigh on your unrelated bug fix the way it would in `CLAUDE.md`." For side-effecting workflows the docs recommend `disable-model-invocation: true` (manual `/name` only). — [Best practices](https://code.claude.com/docs/en/best-practices)
- **[a]** Plan mode: a text search of the full best-practices page returns zero mentions of "plan mode". The nearest equivalent is "Brainstorm with Claude first": have Claude interview you, write `SPEC.md`, then "start a fresh session to build from it, so the build begins with a clean context and a written definition of done." — [Best practices](https://code.claude.com/docs/en/best-practices)
- **[a]** Plan mode is still documented as a permission mode ("Plan mode tells Claude to research and propose changes without making them"), recommended in the modes table for "Exploring a codebase before changing it". New interactive terminal and VS Code sessions start in auto mode (v2.1.283+), not plan mode. — [Claude Code docs: Permission modes](https://code.claude.com/docs/en/permission-modes) (fetched 2026-11-16)
- **[a]** "What you can stop doing" table explicitly retires older advice, including: "The context window is your main constraint, manage it aggressively" (reason: "Most current models have a 1M-token window and compaction happens on its own, so running out is rare. `/clear` between tasks is still worth doing, because a focused context gets you better answers and costs less."); "Add IMPORTANT or ALL CAPS to instructions"; "Use subagents to protect your context window"; "`think hard`... in the prompt"; and "Describe your architecture and file layout in `CLAUDE.md`" (reason: "Claude reads the repo itself. Only write down what isn't in there."). — [Best practices](https://code.claude.com/docs/en/best-practices)
- **[a]** Steering advice: "Watch the first minute, press `Esc` the moment Claude drifts, and after two failed corrections run `/clear` and write a better prompt instead of a third." `/rewind` "makes it low-risk to try the bolder approach first and rewind if it doesn't work out." — [Best practices](https://code.claude.com/docs/en/best-practices)
- **[a]** Recommended adoption order for newcomers: "Start with CLAUDE.md for project conventions, then add other extensions as specific triggers come up." The trigger table lists CLAUDE.md first ("Claude gets a convention or command wrong twice"), then output style, skills, MCP, code intelligence, subagents, hooks, plugins. Rule of thumb: "Keep CLAUDE.md under 200 lines. If it's growing, move reference content to skills or split into `.claude/rules/` files." — [Claude Code docs: Extend Claude Code](https://code.claude.com/docs/en/features-overview) (fetched 2026-11-16)
- **[c]** Boris Cherny (Claude Code creator), X thread of 2 Jan 2026: "My setup might be surprisingly vanilla!"; team shares one checked-in CLAUDE.md and adds to it "whenever Claude does something wrong", "multiple times a week"; "Most sessions start in Plan mode... A good plan is really important!"; and on verification, giving Claude a way to verify its work is "probably the most important" factor and will "2-3x the quality of the final result." — [Thread Reader copy of @bcherny thread](https://threadreaderapp.com/thread/2007179832300581177) (Jan 2026; Opus 4.5 era, so plan-mode emphasis may be outdated; the 2-3x figure is an unmeasured personal estimate)
- **[a]** Anthropic's context-engineering post (29 Sep 2025) frames the general principle: "find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome", and notes "CLAUDE.md files are naively dropped into context up front" while glob/grep retrieve files just-in-time. — [Anthropic Engineering: Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### Inferences
- Anthropic's own ranking in late 2026 is roughly: verification loop > short, high-signal CLAUDE.md > hooks/permissions for hard rules > skills for procedures > `/clear` between tasks. Plan mode and manual context babysitting have been visibly de-emphasised relative to 2025-era guidance (compare Boris Cherny's Jan 2026 "most sessions start in Plan mode" with a Nov 2026 best-practices page that never mentions it).
- The docs are not fully self-consistent: the memory page still lists "project layout" / "project architecture" as CLAUDE.md content, while the best-practices page says to stop describing architecture and file layout there. The best-practices wording is the newer and more specific position.
- All of this is vendor guidance without published measurements; Anthropic gives no numbers for any of these recommendations.

### Gaps
- Could not read the original April 2025 "Claude Code: Best practices for agentic coding" engineering post (URL now redirects; archive blocked), so I cannot quote how the ordering changed between 2025 and 2026.
- Search snippets (not fetched primary sources) say Boris Cherny stated in mid-2026 that he now mostly uses auto mode rather than starting in plan mode; a secondary article paraphrases him as saying plan mode "was useful and is no longer useful" but links no primary source ([MindStudio, 18 Oct 2026](https://www.mindstudio.ai/blog/claude-plan-mode-still-necessary)). I could not verify the original statement. Treat as unconfirmed.
- Pragmatic Engineer coverage (podcast "Building Claude Code with Boris Cherny", 4 Mar 2026; article "How Claude Code is built") was only seen in search results, not read.

## 2. Is there independent evidence on whether CLAUDE.md / AGENTS.md style instruction files help or hurt (including length and adherence)?

### Takeaway
The best controlled study (ETH Zurich, 2026) finds that auto-generated context files do not improve task success and raise cost by roughly 20%, while human-written files give at most a small, statistically non-significant gain; agents do follow the instructions, but repository overviews do not help them navigate. The evidence supports a short, hand-curated file containing only non-discoverable facts and commands, and argues against `/init`-style generated files left unedited; nothing independent supports long files.

### Cited Findings
- **[b]** Gloaguen et al. (ETH Zurich / LogicStar), "Evaluating AGENTS.md" (arXiv v1 12 Feb 2026, v3 29 Sep 2026): abstract states "providing context files does not generally improve task success rates" while "increasing inference cost by over 20% on average"; agents follow the instructions, but overviews do not help; context files are useful for specifying non-standard practices and performance claims "should be rigorously evaluated". — [arXiv:2602.11988 abstract](https://arxiv.org/abs/2602.11988)
- **[b]** Same paper, per-agent results as extracted from the HTML version (Table 5, success %): Claude Code + Sonnet 4.5 on SWE-bench Lite 59.9 (no file) vs 58.7 (LLM-generated file); on the paper's own benchmark of 138 instances from 12 repos with developer-committed files: 73.2 (none) vs 65.2 (LLM-generated) vs 70.3 (developer-written). For Codex GPT-5.2: 65.2 / 68.1 / 68.1; Qwen Code: 45.7 / 47.1 / 53.6. Average effect (computed by the fetch tool from the table): LLM-generated about -0.5 pt (SWE-bench) and -2 pt (own benchmark), developer-written about +2.4 pt, none individually significant (p = 0.87, 0.37, 0.21); developer vs LLM-generated p = 0.038. — [arXiv:2602.11988 HTML](https://arxiv.org/html/2602.11988)
- **[b]** Same paper, cost: Claude Code + Sonnet 4.5 cost rose about 16% (LLM file) and 13% (developer file) with 11-14% more steps. Adherence: tools named in the file are used far more (e.g. `uv` 1.6 uses per instance when mentioned vs under 0.01 when not). Overviews: "context files are not effective at providing a repository overview"; they did not reduce steps to reach the files that needed changing. Recommendation: omit LLM-generated context files for now; human files "should only include instructions required for coding agents that are not already present in the README". — [arXiv:2602.11988 HTML](https://arxiv.org/html/2602.11988)
- **[b]** Same paper, important nuance: when all other documentation was stripped from the repos, LLM-generated files improved performance by 2.7% on average (Claude Code excluded from this ablation for cost). Limitations stated by the authors: Python only, only resolution rate measured (not quality, security, convention adherence), 138 instances / 12 repos. Note: the benchmark name differs between versions (search results for v1 say "AGENTbench"; the current HTML says "CTXbench"), and the fetch tool flagged small text-vs-table inconsistencies (text says developer files beat LLM files by "7% on average"; table implies about 4 points). — [arXiv:2602.11988 HTML](https://arxiv.org/html/2602.11988)
- **[d]** The Hacker News thread on that paper (232 points, 161 comments, early 2026) split: supporters of instruction files argued a ~4% gain from human-written files is large and that on big repos a specific AGENTS.md is "the difference between the agent spending half of its context window searching"; sceptics said the gain is "barely worth the token cost" and that the practice rests on "feelings and wishful thinking"; several noted the study does not measure output quality or convention adherence. A paper author (nielstron) noted the human-written gain was not consistent and that performance drops by over 2% on Sonnet 4.5. — [Hacker News discussion](https://news.ycombinator.com/item?id=47034087)
- **[b]** Lulla et al., "On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents" (arXiv, 28 Jan 2026, v2 30 Mar 2026): across 10 repos and 124 pull requests, AGENTS.md presence was "associated with a lower median runtime" (28.64% lower) and 16.58% lower output-token use, with "comparable task completion behavior". Caveats: abstract-only read; associational wording; small sample; only output tokens reported; which agent was run is not stated in the abstract. This partly conflicts with the ETH finding of more steps and higher cost. — [arXiv:2601.20404](https://arxiv.org/abs/2601.20404)
- **[b]** Vercel (27 Jan 2026) eval on Next.js 16 APIs absent from training data: baseline 53% pass; a docs skill with default behaviour 53% (the skill was never invoked in 56% of cases); skill plus explicit "use it" instructions 79%; a compressed 8KB docs index placed in AGENTS.md 100%. Caveats: vendor-run, agent/model and number of eval cases not stated on the page, Claude Code not confirmed as the agent, and the task is "unknown API knowledge", which is the best case for passive context. — [Vercel blog: AGENTS.md outperforms skills in our agent evals](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- **[b]** Jaroslawicz et al., "How Many Instructions Can LLMs Follow at Once?" (arXiv, 15 Jul 2025): on a 500-keyword-instruction report-writing benchmark across 20 models, the best frontier models "only achieve 68% accuracy at the max density of 500 instructions", with a bias toward earlier instructions. Not a coding-agent study; pre-dates current models. — [arXiv:2507.11538](https://arxiv.org/abs/2507.11538)
- **[c]** HumanLayer ("Kyle", 25 Nov 2025) builds on that paper: "Frontier thinking LLMs can follow ~ 150-200 instructions with reasonable consistency"; "Claude Code's system prompt contains ~50 individual instructions"; Claude Code wraps CLAUDE.md with a reminder that "this context may or may not be relevant to your tasks"; "general consensus is that < 300 lines is best, and shorter is even better"; "our root `CLAUDE.md` file is less than sixty lines"; "avoid auto-generating it"; "Never send an LLM to do a linter's job"; "Prefer pointers to copies". The 150-200 figure is the author's reading of the paper, not a measured Claude Code result. — [HumanLayer: Writing a good CLAUDE.md](https://www.humanlayer.dev/blog/writing-a-good-claude-md)
- **[a]** Anthropic's own docs agree on length and non-enforcement: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence."; "CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself. Claude reads it and tries to follow it, but there's no guarantee of strict compliance, especially for vague or conflicting instructions."; `@path` imports "don't reduce its context cost". No adherence measurements are published. — [Claude Code docs: Memory](https://code.claude.com/docs/en/memory)
- **[a]** `.claude/rules/` with `paths:` frontmatter "only load into context when Claude works with matching files, reducing noise and saving context space"; but path-scoped rules and nested CLAUDE.md are summarised away on compaction and reload only when a matching file is touched again. — [Memory](https://code.claude.com/docs/en/memory); [Context window](https://code.claude.com/docs/en/context-window)
- **[a]** Auto memory: on by default in local sessions; Claude writes notes of type user/feedback/project/reference to `~/.claude/projects/<project>/memory/`; "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first, are loaded at the start of every conversation"; it is machine-local, not shared across machines or cloud environments; "Claude doesn't save something every session." — [Memory](https://code.claude.com/docs/en/memory)
- **[d]** Auto memory failure mode reported by one developer (8 Feb 2026): MEMORY.md is edited read-modify-write with "No locking, no compare-and-swap, no merge strategy", so parallel agents can silently lose updates; "You won't know something was lost until a future session acts on stale or missing knowledge." Evidence is a reasoned race scenario, not logs or a reproduction. — [DEV Community: Auto Memory, Auto Forget](https://dev.to/wkusnierczyk/auto-memory-auto-forget-g05)
- **[b]** Descriptive study of what people actually put in these files: Chatlatanagulchai et al., "Agent READMEs" (arXiv, 17 Nov 2025; v2 9 Aug 2026), 2,303 context files from 1,925 repos: files evolve like configuration code through frequent small additions; most common content is test procedures (75.9%), implementation details (70.8%) and architecture (68.1%); security (14.8%) and performance (14.5%) are rarely specified; files are described as complex and hard to read. Abstract-only read. — [arXiv:2511.12884](https://arxiv.org/abs/2511.12884)

### Inferences
- Verified fact pattern: (1) agents obey instruction files (ETH adherence data), (2) generic/generated overviews add cost without improving success, (3) curated, non-discoverable content gives a small positive or neutral effect on pass rate, and a large effect when the content is knowledge the model cannot have (Vercel). So the value of CLAUDE.md is almost entirely in its content selection, not its existence.
- The architecture-overview content that 68% of real-world files contain (Agent READMEs study) is exactly the category the ETH study found unhelpful and that Anthropic now tells users to delete. A large share of CLAUDE.md files in the wild are therefore probably net-negative on cost and neutral on success.
- No study measures what practitioners say they use the file for: convention adherence, fewer repeated corrections, code-review churn. The ETH resolution-rate metric cannot see those, so "does not help" is established only for task success on Python issue-fixing.
- Evidence for a specific line limit is weak. "Under 200 lines" (Anthropic) and "under 300 / ~150-200 instructions" (HumanLayer) are rules of thumb; the only measurement behind them is a non-coding instruction-density benchmark from mid-2025.
- The ETH (more steps, +20% cost) and Lulla et al. (-28% runtime) results point in opposite directions on efficiency; the ETH design is the more controlled of the two, and the Lulla result is associational on a small sample.

### Gaps
- No independent measurement of CLAUDE.md length versus adherence inside Claude Code specifically.
- No independent evaluation of auto memory quality (precision of what it saves, staleness rates) or of `.claude/rules` path scoping. Auto memory evidence is vendor docs plus a few anecdotes; several third-party blog claims about stale-memory bugs in specific versions were seen only in search snippets and are not cited.
- The ETH study used Sonnet 4.5 for Claude Code; no replication on the current default models was found.
- No large practitioner survey on instruction-file usefulness was found.

## 3. What is the evidence that plan mode (plan first, then execute) improves results, and what do critics say?

### Takeaway
There is no controlled measurement of Claude Code's plan mode. Adjacent research shows that a good plan improves agent success and a poor plan is worse than none; practitioner support is strong for planning as a human review checkpoint on large or ambiguous work, but credible critics argue plan mode itself is a thin prompt wrapper that you can replace with "write a plan to a file", and Anthropic's late-2026 guidance no longer features it.

### Cited Findings
- **[b]** Liu et al., "From Plan to Action" (arXiv, 13 Apr 2026; v3 7 Aug 2026): 21,120 SWE-agent trajectories, four LLMs, SWE-bench Verified and Pro, eight plan variations. Providing a standard plan improves issue resolution; periodic plan reminders reduce violations and improve success; a subpar plan "hurts performance more than no plan at all"; adding extra early phases can degrade performance when they do not match the model's internal strategy. This is SWE-agent with supplied plans, not Claude Code plan mode, and abstract-only read (a search snippet cited 16,991 trajectories for v1). — [arXiv:2604.12147](https://arxiv.org/abs/2604.12147)
- **[c]** Boris Cherny, 2 Jan 2026: "Most sessions start in Plan mode"; iterate on the plan, then switch to auto-accept and Claude "can usually 1-shot it"; "A good plan is really important!" Personal workflow report on Opus 4.5, no measurement. — [Thread Reader copy of @bcherny thread](https://threadreaderapp.com/thread/2007179832300581177)
- **[c]** Armin Ronacher, 17 Dec 2025, reverse-engineered plan mode: a plan is "effectively a markdown file that is written into Claude's plans folder"; entering plan mode injects a read-only instruction with "no other enforcement from what I can tell"; "it is in fact just a rather short predefined prompt". He asks "why can I not just ask the model to plan with me?", says he "never really used plan mode", prefers a plan file on disk he can edit ("I feel like I'm more in control of that experience"), and finds the integrated UX "a little bit too far away from me to feel natural". The only non-replicable part he identifies is the built-in approval UI. Enforcement details may have changed since Dec 2025. — [Armin Ronacher: What Actually Is Claude Code's Plan Mode?](https://lucumr.pocoo.org/2025/12/17/what-is-plan-mode/)
- **[c]** HumanLayer (Dex Horthy), mid-2025: the case for plan review is leverage: "a bad line of a plan could lead to hundreds of bad lines of code"; "I can't read 2000 lines of golang daily. But I can read 200 lines of a well-written implementation plan." Their research-plan-implement workflow uses plan files on disk rather than plan mode per se. Claimed outcomes (35k LOC shipped to a 300k LOC Rust codebase in about 7 hours) are self-reported, single-team. — [HumanLayer: Advanced Context Engineering for Coding Agents](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)
- **[a]** Current docs (Nov 2026): plan mode "tells Claude to research and propose changes without making them"; recommended for "Exploring a codebase before changing it"; plans are files in `~/.claude/plans/` and are re-injected after compaction; approval options hand off to auto mode / auto-accept / manual; an optional setting adds "approve and clear planning context". Limit: "In interactive terminal sessions with bypass permissions available, Claude Code also doesn't enforce plan mode's blocks. Claude is still instructed to plan without editing, but a file edit or shell command it attempts during planning runs without prompting." — [Permission modes](https://code.claude.com/docs/en/permission-modes); [Context window](https://code.claude.com/docs/en/context-window)
- **[a]** The Nov 2026 best-practices page does not mention plan mode; it recommends an interview-to-`SPEC.md` step followed by a fresh session, and says current models "usually carry on through an agreed task without being told". — [Best practices](https://code.claude.com/docs/en/best-practices)
- **[c/d]** A vendor-blog article (MindStudio, 18 Oct 2026) argues plan mode's remaining function is a gate, "not a reasoning aid": useful for big, unclear, multi-file tasks where a misunderstood scope is expensive; skip it for small, clearly scoped changes. It attributes to Boris Cherny the view that plan mode "was useful and is no longer useful" without a quote or link. — [MindStudio: Is Claude plan mode still necessary?](https://www.mindstudio.ai/blog/claude-plan-mode-still-necessary)

### Inferences
- The defensible claim is about plan quality and human review, not about the mode: research says good plans help and bad plans hurt, so an unreviewed auto-generated plan is not automatically a win. The benefit of plan mode is the forced pause where a human catches a wrong approach before code is written.
- Plan mode's marginal value has probably fallen through 2026 as models plan implicitly and auto mode became the default; the vendor's own guidance drifted from "start in plan mode" (creator, Jan 2026) to not mentioning it (docs, Nov 2026). This is an inference from documentation changes plus unverified secondary reports.
- Plan mode is not a safety boundary. By Anthropic's own docs it is unenforced in bypass-permissions terminal sessions, and by Ronacher's Dec 2025 analysis it was prompt-level only.

### Gaps
- No controlled comparison of Claude Code with versus without plan mode on any benchmark was found. Blog claims such as "plan mode 2-3x success rate" appeared in search results only; they appear to trace back to Boris Cherny's verification quote or unsourced estimates and were not fetched.
- Could not confirm Boris Cherny's reported mid-2026 shift away from starting in plan mode from a primary source.
- No data on how often plans are followed or deviated from inside Claude Code.

## 4. What is the evidence for Skills being useful (adoption, progressive disclosure and context cost, failure modes such as not triggering)?

### Takeaway
Curated skills measurably help: SkillsBench reports about +17 points pass rate on average and +18 points for Claude Code, though software-engineering tasks gain least and model-written skills make results worse. The well-documented weakness is automatic triggering: independent tests show skills are ignored roughly half the time without explicit invocation or a forcing hook, so skills are reliable as manually invoked workflows and unreliable as passive knowledge.

### Cited Findings
- **[b]** SkillsBench (Li et al., 77 authors; arXiv v1 13 Feb 2026, v4 14 Jun 2026): 87 tasks, 8 domains, 18 model-harness configurations with deterministic verifiers. Average pass rate rose from 33.9% to 50.5% with curated skills (+16.6 pp); configuration-level gains ranged +4.1 to +25.7 pp; "Focused Skills with at most three modules outperform larger or exhaustive bundles"; smaller models with skills can match larger models without. (Earlier versions reported 84-86 tasks, 7 configurations and +16.2 pp.) — [arXiv:2602.12670 abstract](https://arxiv.org/abs/2602.12670)
- **[b]** SkillsBench body (v4 HTML): Claude Code + Opus 4.7 scored 43.0% without skills and 61.2% with curated skills (+18.2 pp). Self-generated skills were worse than no skills: Claude Code -8.1 pp, Codex + GPT-5.5 -11.3 pp, Gemini CLI -11.5 pp (average about -10.3 pp, computed by the fetch tool). 13 of 87 tasks got worse with curated skills. Software Engineering gained +11.6 pp (37.6% to 49.2%), seventh of eight domains; natural science gained +28.8 pp. One skill +18.0 pp, two to three +19.0 pp, four or more only +10.1 pp; "comprehensive documentation" style skills gained only +0.7 pp. Authors' caveats: gains could partly reflect added context rather than procedural structure (no length-matched control); benchmark skills are far higher quality than the ecosystem average (10.1/12 vs 6.2/12 on their rubric), so results are an optimistic scenario; some harnesses acknowledge skill content but proceed without invoking it. — [arXiv:2602.12670 HTML](https://arxiv.org/html/2602.12670)
- **[b]** Scott Spence (8 Feb 2026), sandboxed activation test, Claude Sonnet 4.5 via `claude -p`, 22 prompts, 4 Svelte skills, two runs (about 250 invocations, $5.59): with no hook the correct skill activated 55% and 50% of the time; a simple reminder hook 59% / 50%; a "forced-eval" hook 100% / 100%; an LLM pre-classifier hook 100% / 100% but with 4 false positives on 5 no-skill prompts in a harder set. On 24 harder prompts forced-eval reached 75%. Author's own caveat: "slightly more than an anecdote"; 20-second, single-turn runs measure activation only, not output quality. — [Scott Spence: Measuring Claude Code Skill Activation With Sandboxed Evals](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)
- **[b]** Vercel (27 Jan 2026): a docs skill was never invoked in 56% of eval cases and produced no gain over baseline (53% vs 53%); explicit instructions raised it to 79%, with strong wording sensitivity ("MUST invoke" made the agent read docs first and miss project context); always-loaded AGENTS.md content reached 100%. Vercel's stated explanation: passive context removes the decision of whether to look something up. They add that skills remain suited to user-triggered vertical workflows (e.g. framework upgrades). Agent/model not named. — [Vercel blog](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- **[a]** Progressive disclosure as designed: name and description are preloaded; SKILL.md body loads when judged relevant; linked files load "only as needed"; "the amount of context that can be bundled into a skill is effectively unbounded." No token measurements are given. Security caveat: "malicious skills may introduce vulnerabilities" and may "direct Claude to exfiltrate data"; install "only from trusted sources". — [Anthropic Engineering: Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) (16 Oct 2025; updated 18 Dec 2025 noting Agent Skills published as an open standard)
- **[a]** Context cost and limits per current docs: skill descriptions are in every request; each entry's description plus `when_to_use` is capped at 1,536 characters; the whole listing has a budget that "scales at 1% of the model's context window", and when it overflows "Claude Code drops descriptions starting with the skills you invoke least", removing the keywords needed for matching; "Keep `SKILL.md` under 500 lines"; "Once a skill loads, its content stays in context across turns, so every line is a recurring token cost." — [Claude Code docs: Skills](https://code.claude.com/docs/en/skills)
- **[a]** Docs acknowledge the triggering and persistence failure modes: a "Skill not triggering" section (fix: keyword-rich descriptions, or "Invoke it directly with `/skill-name`"); "If descriptions are vague or overlap, Claude may load the wrong skill or miss one that would help"; "Claude stops following a skill" (skill text is not re-read on later turns; must-hold rules belong in hooks); after compaction each invoked skill is re-attached but capped at 5,000 tokens with a 25,000-token total, "so older skills can be dropped entirely after compaction". Custom slash commands have been merged into skills. — [Skills](https://code.claude.com/docs/en/skills); [Extend Claude Code](https://code.claude.com/docs/en/features-overview); [Context window](https://code.claude.com/docs/en/context-window)
- **[c]** Simon Willison, 16 Oct 2025: "Claude Skills are awesome, maybe a bigger deal than MCP"; each skill "only takes up a few dozen extra tokens" at session start, versus GitHub's MCP server which "famously consumes tens of thousands of tokens"; the mechanism is "entirely dependent on the model having access to a filesystem"; on safety, the word "safe" in safe coding environments "is doing a lot of work". This is a launch-week assessment of the design, not a usage report. — [Simon Willison: Claude Skills are awesome, maybe a bigger deal than MCP](https://simonwillison.net/2025/Oct/16/claude-skills/)
- **[c]** Boris Cherny, 2 Jan 2026: uses checked-in slash commands for repeated workflows; his commit-push-pr command is used "dozens of times every day". This is the manually invoked form (now unified with skills). — [Thread Reader copy of @bcherny thread](https://threadreaderapp.com/thread/2007179832300581177)
- **[d]** GitHub issue #13919 (opened 13 Dec 2025, v2.0.69): after auto-compaction Claude "completely loses awareness of Claude Skills that were actively being used"; reporter claims a one-hour task took 5-6+ hours. 15 comments, 5 thumbs-up, no Anthropic staff reply, closed "not planned" by a bot for inactivity on 7 May 2026. Docs now describe post-compaction re-attachment of skills (and re-injection of skill descriptions from v2.1.304), which suggests this was at least partly addressed, with the token caps above as the remaining limit. — [anthropics/claude-code#13919](https://github.com/anthropics/claude-code/issues/13919)

### Inferences
- Two distinct uses of skills have very different evidence: (1) user-invoked workflows (`/release`, `/commit-push-pr`) are deterministic to trigger, cheap, and endorsed by vendor and practitioners; (2) model-invoked "knowledge" skills depend on auto-triggering that independent tests put at around 50% (Sonnet 4.5, early 2026) and that Vercel found lost to always-on context for must-know facts.
- Asking Claude to write its own skills and leaving them unreviewed is contraindicated by the one benchmark that tested it (self-generated skills -8 to -11 pp).
- Skill sprawl is self-defeating: the listing budget drops descriptions of rarely used skills, and SkillsBench shows four-plus skills or comprehensive skills gain much less than one to three focused ones.
- Software engineering was among the lowest-gaining domains in SkillsBench, consistent with Anthropic's own advice that skills are for what the model cannot know (team procedures), not general engineering knowledge.
- The "context cost is near zero" claim is true per skill (dozens of tokens to a 1,536-character cap) but an invoked skill's full body persists for the rest of the session.

### Gaps
- No trustworthy adoption statistics were found; marketplace and star counts were deliberately not used.
- Activation-rate tests were on Sonnet 4.5 / early-2026 harness versions; no re-test on the current default models was found, so the ~50% figure may be outdated.
- No independent measurement of token overhead from large skill libraries in real sessions.
- A third-party post claiming an audit of 214 skills found 73% "silently broken" appeared in search results only and was not read or cited.

## 5. What do practitioners report about context management: /clear versus /compact, context rot, and quality loss after auto-compaction?

### Takeaway
Context rot is real and independently measured in general LLM settings, and both vendor and practitioners converge on the same practical rule: start fresh (`/clear` or a new session with a written handoff) between tasks rather than relying on compaction. Auto-compaction is a convenience with a documented cost: it is lossy, and the one Claude Code-specific dataset found user corrections more than doubled after compaction; however, 1M-token windows have made running out of context much rarer than the 2025 advice assumed.

### Cited Findings
- **[b]** Chroma, "Context Rot" (14 Jul 2025): 18 models including Claude Opus 4, Sonnet 4, Sonnet 3.7; "model performance varies significantly as input length changes, even on simple tasks"; "Even a single distractor reduces performance relative to the baseline"; Claude models "tend to abstain when uncertain" and had the lowest hallucination rates. Not about coding agents (needle-in-haystack, LongMemEval, repeated words); vendor of a retrieval database; pre-dates current models; mechanisms unexplained. — [Chroma Research: Context Rot](https://www.trychroma.com/research/context-rot)
- **[a]** Anthropic (29 Sep 2025) accepts the phenomenon: "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases"; on compaction, "overly aggressive compaction can result in the loss of subtle but critical context"; clearing old tool results is "one of the safest lightest touch forms of compaction". — [Anthropic Engineering: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **[b]** LangWatch (Rogerio Chaves, 2 Aug 2026), one developer's Claude Code telemetry over 162 days: 2,451 sessions, 287,748 API calls, 873 compaction events. In the five steps after a compaction, 41.9% of user messages contained a correction versus a 17.7% baseline (about 2.4x), still elevated after 30 steps and not recovered by 120; tool-error rate was flat. Median compaction shrank a 574,875-token window to a 4,382-token summary. Cost grew with context at a power-law exponent of about 2.55; context actually used per step stayed around 8,000 tokens; the cost-optimal compaction point was about 220K tokens (suggested range 200K-450K by task). Caveats stated by the author: single user, observational (he sometimes compacts when things are already going badly), corrections are a proxy, vendor promoting its tracking product. — [LangWatch: Context tax, when to compact](https://langwatch.ai/blog/context-tax-when-to-compact)
- **[c]** HumanLayer (Dex Horthy, mid-2025): "frequent intentional compaction" means "designing your ENTIRE WORKFLOW around context management", "keeping utilization in the 40%-60% range"; instead of relying on built-in compaction, have the agent "Write everything we did so far to progress.md" and continue from that in a fresh context; the worst things for a context window, in order, are incorrect information, missing information, then too much noise. Written for 200K-window models; the 40-60% figure is a heuristic, not a measurement. — [HumanLayer: Advanced Context Engineering for Coding Agents](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)
- **[a]** Current vendor position on `/clear` vs `/compact`: "`/clear` between unrelated tasks. It costs nothing, and it means the next task doesn't keep paying for the previous one's history."; "`/compact` with a focus... On a long session `/compact` is itself a big request, since it reads the whole conversation to summarize it"; "If you've corrected the same thing twice and it's still wrong... `/clear` plus one new prompt that folds in what you learned works better almost every time."; "With a 1M-token window on most current models and compaction near the top of it, you'll rarely run out of context. You can still *pay* for context you don't need". — [Best practices](https://code.claude.com/docs/en/best-practices)
- **[a]** What compaction loses, per docs: "The summary keeps your requests and key code snippets, but detailed instructions from early in the conversation may be lost. Put persistent rules in CLAUDE.md rather than relying on conversation history." Survives: system prompt, project-root CLAUDE.md and unscoped rules (re-injected from disk), auto memory, the plan-mode plan, skill descriptions (v2.1.304+). Partially survives: up to five most recently modified files are re-read (files over 5,000 tokens come back as a path only); invoked skill bodies capped at 5,000 tokens each / 25,000 total. Lost until re-triggered: path-scoped rules and nested CLAUDE.md. Even conversational safety instructions can vanish: "the sentence can get lost when the conversation compacts, so anything that matters belongs in a deny rule." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works); [Context window](https://code.claude.com/docs/en/context-window); [Best practices](https://code.claude.com/docs/en/best-practices)
- **[a]** Tools available: `/context` (live breakdown by category), `/compact <focus>`, a "Compact Instructions" section in CLAUDE.md, `/autocompact <tokens>` to compact earlier, `/rewind` then "Summarize from here / up to here" for partial compaction, `/btw` for side questions that add nothing to history; sessions idle past about 200K tokens on the one-hour cache are compacted before the cache expires. — [Context window](https://code.claude.com/docs/en/context-window); [Best practices](https://code.claude.com/docs/en/best-practices)
- **[d]** Community signal on compaction loss: a search of anthropics/claude-code issues surfaced well over a dozen separate reports from 2025 to 2026 titled along the lines of "Claude forgets everything in CLAUDE.md after compaction", "Auto-compact loses instructions from the last user request", and "Please re-read CLAUDE.md after conversation compaction" (issue numbers seen in search results include #1027, #4017, #5731, #6354, #9796, #10006, #14626, #22376, #23063, #24460, #24572, #31409, #36068). I read only #13919 in full (15 comments, bot-closed as "not planned", no staff reply). High volume and consistency, but individually unverified; the CLAUDE.md-specific complaint appears to be addressed by the documented re-injection of project-root CLAUDE.md. — [anthropics/claude-code#13919](https://github.com/anthropics/claude-code/issues/13919) (others seen only as search-result titles)

### Inferences
- Ranking of context habits by evidence: (1) `/clear` or a new session between unrelated tasks (vendor + practitioners + cost data, no real downside); (2) writing state to a file (spec, plan, progress.md) before clearing, which sidesteps lossy summaries (practitioner consensus; consistent with docs re-injecting plan files and CLAUDE.md); (3) focused manual `/compact` mid-task; (4) relying on auto-compaction, which is the fallback and the best-documented source of quality loss.
- The 2025-era advice to obsessively keep utilisation at 40-60% was calibrated to 200K windows. With 1M windows the binding constraints are cost (LangWatch: roughly 6x per doubling) and focus, not overflow. Anthropic now explicitly says aggressive context management is no longer needed, but LangWatch's data suggest compacting or clearing well before the 1M ceiling (around 200K-450K) is still cheaper and that quality after a huge-window compaction is poor.
- Context rot is established for retrieval-style tasks on 2025 models; its magnitude for current coding agents on 1M windows is not independently measured. Anthropic's own remark that "a focused context gets you better answers" is consistent with it persisting.
- `/context` has no outcome evidence of its own; it is a diagnostic that makes the other habits possible.

### Gaps
- No controlled study comparing task outcomes for `/clear` + handoff file versus `/compact` versus auto-compaction in Claude Code.
- Nothing citable was found from Thorsten Ball or Geoffrey Huntley on compaction (Huntley's view that quality degrades as the window fills was seen only second-hand in search snippets).
- No Reddit threads were fetched; r/ClaudeAI and r/ClaudeCode sentiment is not represented beyond what GitHub issues show.
- The auto-compaction threshold values per model were not retrieved (docs point to a separate model-config page).

## 6. How reliable are checkpoints and /rewind, and what are their limits?

### Takeaway
Checkpoints are a useful in-session undo for edits made through Claude's own edit tools, but they are officially not a substitute for git and have large documented blind spots (Bash-made changes, most subagent edits, side effects, symlinks). There are also open, unanswered bug reports of "Restore code" not appearing, including one alleging that auto mode (now the default) steers edits through Bash and thereby silently disables rewind.

### Cited Findings
- **[a]** How it works: a checkpoint is created at every user prompt that starts a turn; the 100 most recent per session are kept; snapshots persist across resume and are deleted about 30 days after last use (`cleanupPeriodDays`). `/rewind` (alias `/undo`, or Esc twice) offers restore code and conversation, conversation only, code only, or "Summarize from here / up to here". — [Claude Code docs: Checkpointing](https://code.claude.com/docs/en/checkpointing) (fetched 2026-11-16)
- **[a]** Documented limits: "A file that only Bash commands changed isn't tracked and stays as it is"; subagent edits are usually not captured ("The subagent's edits to other files stay, so use version control"), including background forked skills and background `/code-review --fix`; manual edits and other concurrent sessions are not tracked; messages typed mid-turn have no checkpoint of their own; symlinked and hard-linked files (dotfile managers, pnpm) are skipped; "Checkpoints are designed for quick, session-level recovery. For permanent version history and collaboration, continue using version control". — [Checkpointing](https://code.claude.com/docs/en/checkpointing)
- **[a]** Side effects are out of scope: "Actions that affect remote systems (databases, APIs, deployments) can't be checkpointed." The best-practices page carries a warning box: "Checkpoints cover the files Claude edited with its own file tools in your main conversation... They work alongside git rather than replacing it." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works); [Best practices](https://code.claude.com/docs/en/best-practices)
- **[a]** Claimed benefit: `/rewind` "makes it low-risk to try the bolder approach first and rewind if it doesn't work out"; use cases listed are exploring alternatives, recovering from mistakes, and freeing context by summarising part of a session. — [Best practices](https://code.claude.com/docs/en/best-practices); [Checkpointing](https://code.claude.com/docs/en/checkpointing)
- **[d]** GitHub issue #14002 (opened 15 Dec 2025, still open Nov 2026): "/rewind shows 'Restore code' option intermittently or fails to restore files"; debug logs show a snapshot "tracking 0 files" created before the modification is registered; about 11 thumbs-up, 6 comments spanning Jan to Sep 2026 including reports on Claude Desktop and "seems to have been broken for months"; no Anthropic staff response. — [anthropics/claude-code#14002](https://github.com/anthropics/claude-code/issues/14002)
- **[d]** GitHub issue #94657 (opened 16 Sep 2026, v2.1.273, open, marked stale by bot 9 Nov 2026, 3 thumbs-up, no staff response): reporter says auto mode injects an instruction to "make file changes with sed, heredocs, or short scripts, rather than using the dedicated Read, Edit, or Write tools", so in one session with 124 prompts there were 96 Bash calls, 0 Edit/Write calls, and 14 snapshots all with empty tracked-file lists: "auto mode steers the model toward the one editing path that checkpointing cannot see, silently disabling rewind for the whole session." Single report, not confirmed by Anthropic, and the docs page now says rewind does undo later Bash changes to files Claude had already edited with its edit tools. — [anthropics/claude-code#94657](https://github.com/anthropics/claude-code/issues/94657)

### Inferences
- Verified facts: the coverage gaps are documented by the vendor. Opinion/inference: because auto mode and background subagents are now defaults, the share of changes that fall outside checkpoint coverage has likely grown through 2026, making git commits (or worktrees) the only dependable undo for agentic sessions.
- The conversation-side functions of `/rewind` (rewind conversation, partial summarise) do not depend on file tracking and are probably the more reliable half of the feature; I found no bug reports against them, but also did not search specifically.
- Volume of complaints is modest (single-digit to low-double-digit reactions) compared with compaction complaints; this is weak evidence either of acceptable reliability or of low usage.

### Gaps
- No independent test of checkpoint restore reliability across versions; no practitioner with a track record was found writing in depth about `/rewind`.
- Whether issue #94657's auto-mode/Bash interaction still reproduces on current versions is unknown.
- No usage data on how often developers actually use `/rewind` versus git.

## 7. For each feature: known downsides, who benefits most, and a provisional must-use / situational / overhyped ranking

### Takeaway
On the evidence gathered, the must-use items are a short hand-curated CLAUDE.md centred on verification commands and `/clear` between tasks; skills as manually invoked workflows and planning-with-review on large tasks are situational but well supported; auto-triggered knowledge skills, unedited `/init` output, long CLAUDE.md files, plan mode as a default ritual, and trust in auto-compaction or checkpoints as safety nets are the overhyped parts.

### Cited Findings
- **CLAUDE.md (hand-curated, short)** — For: agents follow it (tool usage 1.6 vs <0.01 per instance when mentioned) [b] [arXiv:2602.11988](https://arxiv.org/html/2602.11988); developer-written files about +2.4 pt, not significant [b] (same); passive always-on context beat skills 100% vs 79% vs 53% for unknown-API knowledge [b] [Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals); team "mistake ledger" practice [c] [Boris Cherny thread](https://threadreaderapp.com/thread/2007179832300581177). Against: +13-16% cost and more steps for Claude Code [b] [arXiv:2602.11988](https://arxiv.org/html/2602.11988); "Longer files consume more context and reduce adherence" and compliance is not guaranteed [a] [Memory docs](https://code.claude.com/docs/en/memory).
- **CLAUDE.md (auto-generated via `/init`, or long/overview-heavy)** — Against: LLM-generated files lowered Claude Code success 73.2 to 65.2 on the paper's benchmark and added ~16% cost; overviews do not help navigation [b] [arXiv:2602.11988](https://arxiv.org/html/2602.11988); "avoid auto-generating it" [c] [HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md); Anthropic itself: after `/init` "the work is mostly removing lines" and stop describing architecture and file layout [a] [Best practices](https://code.claude.com/docs/en/best-practices). For: generated files helped (+2.7%) only when the repo had no other documentation [b] [arXiv:2602.11988](https://arxiv.org/html/2602.11988).
- **`.claude/rules` (path-scoped)** — For: loads only with matching files, reducing always-on context [a] [Memory docs](https://code.claude.com/docs/en/memory). Against: dropped on compaction until a matching file is touched again; on-demand files over a per-file size limit are truncated [a] [Context window](https://code.claude.com/docs/en/context-window), [Memory docs](https://code.claude.com/docs/en/memory). No independent evidence either way.
- **Auto memory** — For: zero-effort capture of corrections and preferences, on by default [a] [Memory docs](https://code.claude.com/docs/en/memory). Against: only first 200 lines/25KB of the index load; machine-local so not shared with teammates or cloud sessions; saving is at Claude's discretion [a] (same); possible silent lost updates with parallel agents [d] [DEV Community](https://dev.to/wkusnierczyk/auto-memory-auto-forget-g05). No independent quality evidence.
- **Skills (user-invoked workflows / former slash commands)** — For: curated skills +18.2 pp for Claude Code on SkillsBench [b] [arXiv:2602.12670](https://arxiv.org/html/2602.12670); used "dozens of times every day" by the Claude Code team [c] [Boris Cherny thread](https://threadreaderapp.com/thread/2007179832300581177); low idle context cost [a] [Extend Claude Code](https://code.claude.com/docs/en/features-overview). Against: 13 of 87 tasks got worse; four-plus or comprehensive skills gain little; SWE domain gains least [b] [arXiv:2602.12670](https://arxiv.org/html/2602.12670); supply-chain/prompt-injection risk from third-party skills [a] [Anthropic skills post](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills), [c] [Simon Willison](https://simonwillison.net/2025/Oct/16/claude-skills/).
- **Skills (auto-triggered knowledge)** — Against: ~50-55% activation without a forcing hook (Sonnet 4.5) [b] [Scott Spence](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals); never invoked in 56% of cases [b] [Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals); self-generated skills -8.1 pp for Claude Code [b] [arXiv:2602.12670](https://arxiv.org/html/2602.12670); descriptions dropped when the listing exceeds 1% of the context window [a] [Skills docs](https://code.claude.com/docs/en/skills). For: forcing hooks reached 100% on standard prompts [b] [Scott Spence](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals).
- **Plan mode / plan-first** — For: good plans improve resolution in SWE-agent [b] [arXiv:2604.12147](https://arxiv.org/abs/2604.12147); plan review gives more leverage than code review [c] [HumanLayer ACE](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md); creator's Jan 2026 default [c] [Boris Cherny thread](https://threadreaderapp.com/thread/2007179832300581177). Against: poor plans are worse than none [b] [arXiv:2604.12147](https://arxiv.org/abs/2604.12147); plan mode is a short prompt you can replicate with a file [c] [Armin Ronacher](https://lucumr.pocoo.org/2025/12/17/what-is-plan-mode/); not enforced under bypass permissions [a] [Permission modes](https://code.claude.com/docs/en/permission-modes); absent from the current best-practices page [a] [Best practices](https://code.claude.com/docs/en/best-practices).
- **`/clear` and fresh sessions** — For: "costs nothing"; better after two failed corrections [a] [Best practices](https://code.claude.com/docs/en/best-practices); context cost grows super-linearly while useful context stays ~8K tokens [b] [LangWatch](https://langwatch.ai/blog/context-tax-when-to-compact); context rot [b] [Chroma](https://www.trychroma.com/research/context-rot). Against: loses conversational state unless written to a file first (implied by [c] [HumanLayer ACE](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)).
- **`/compact` and auto-compaction** — For: keeps long sessions alive without user effort [a] [Best practices](https://code.claude.com/docs/en/best-practices). Against: early instructions "may be lost" [a] [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works); correction rate 41.9% vs 17.7% after compaction in one user's data [b] [LangWatch](https://langwatch.ai/blog/context-tax-when-to-compact); `/compact` on a long session is itself an expensive request [a] [Best practices](https://code.claude.com/docs/en/best-practices); many user bug reports [d] [anthropics/claude-code#13919](https://github.com/anthropics/claude-code/issues/13919).
- **Checkpoints and `/rewind`** — For: cheap in-session undo and partial summarise [a] [Checkpointing](https://code.claude.com/docs/en/checkpointing). Against: Bash-only changes, most subagent edits, external side effects, symlinks not covered [a] (same); open reports of restore not being offered [d] [#14002](https://github.com/anthropics/claude-code/issues/14002), [#94657](https://github.com/anthropics/claude-code/issues/94657).

### Inferences
Provisional ranking (my synthesis; opinion, not a measured result):

- **Must-use**
  - A short, hand-written CLAUDE.md containing only non-discoverable facts and, above all, the exact test/lint/typecheck commands. Suits everyone; highest payoff for teams (shared, reviewed in git) and for repos with unusual tooling. Evidence grade: moderate (adherence measured; success effect small; vendor and practitioners agree on content rules).
  - `/clear` or a new session between unrelated tasks and after two failed corrections. Suits everyone; free. Evidence grade: moderate (general context-rot studies, one Claude Code cost/quality dataset, vendor guidance).
  - Not in scope but unavoidable in the evidence: giving Claude a runnable check is what both Anthropic and Boris Cherny rank first; CLAUDE.md's main job is to carry that command.
- **Situational (good when matched to the use)**
  - Skills as explicitly invoked workflows for repeated team procedures. Best for experienced developers and teams with recurring multi-step processes; little value for a solo beginner with nothing to encode yet. Keep to a few focused skills.
  - Planning with human review of a written plan/spec for large, ambiguous, multi-file work. Best for experienced developers who can judge a plan; beginners may approve bad plans, which research suggests is worse than no plan. Whether you use plan mode or a markdown file is a UX preference.
  - Focused manual `/compact` or `/rewind` partial summarise in the middle of a single long task; `/context` as a diagnostic.
  - `.claude/rules` path scoping for large monorepos/teams (no independent evidence; mechanism is sound, but rules vanish on compaction).
  - Checkpoints for quick undo of straightforward edit-tool changes, alongside git, never instead of it. Most useful to beginners who do not commit often, who are also the group most exposed to its blind spots.
  - Auto memory: harmless default for a solo developer on one machine; of limited value for teams (not shared) and needs occasional pruning. Evidence is thin in both directions.
- **Overhyped (or at least oversold relative to evidence)**
  - `/init`-generated or long, architecture-heavy CLAUDE.md files left as generated: measured as neutral-to-negative on success and positive on cost.
  - Auto-triggered "knowledge" skills and large installed skill libraries: unreliable activation, description-budget truncation, and negative results for self-generated skills.
  - Plan mode as an always-on ritual for every task, and plan mode as a safety boundary.
  - Auto-compaction as a way to work indefinitely in one session, and elaborate manual context budgeting carried over from the 200K-window era.
  - Checkpoints as a safety net for agentic (auto mode, subagent, Bash-heavy) sessions.

Who benefits most, in short: solo beginners get most from defaults plus a tiny CLAUDE.md and the `/clear` habit; experienced developers gain most from plan/spec review and a handful of invoked skills; teams gain most from a shared, pruned CLAUDE.md, path-scoped rules, and checked-in skills, and least from machine-local auto memory.

### Gaps
- No single study compares these features against each other on the same tasks, so the ranking combines unlike evidence (benchmarks on 2025-2026 models, one-person telemetry, vendor guidance, practitioner opinion).
- Nearly all quantitative evidence pre-dates the models and defaults current on 16 November 2026 (Opus 5.5 default, 1M windows, auto mode default, native AGENTS.md support). Effects that depend on model capability, particularly skill auto-activation rates, the value of explicit planning, and context-rot severity, may have shifted.
- No large practitioner survey was found for any of the features; team-level outcomes (review churn, onboarding time, convention adherence) are unmeasured.
- Sources suggested in the brief that I could not use: the original Anthropic best-practices engineering post (redirects), Pragmatic Engineer (not fetched), Thorsten Ball and Geoffrey Huntley (nothing citable found), Reddit threads (not fetched).
